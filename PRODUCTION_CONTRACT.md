# Locale And Lyrics Production Contract

This document records what the pjsk.moe main site and production operators depend on: the public file paths and their JSON shapes, the cache/ETag/CORS policy, the strict editor gate, the applied migration list, the offline module boundary, backup scope, and the standalone image invariants. `LEGACY_BASELINE.md` remains authoritative for requests without an explicit locale and for all existing public bytes.

## Public Files

Legacy `/files/translation/*` and `/translation/*` generation, ETags, CORS, and cache policy are unchanged. `/translation/<suffix>` is a backward-compatible alias for `/files/translation/<suffix>`; `/translation/lyrics` and `/translation/lyrics/` are literal aliases for `/translation/lyrics/index.json`.

Additive assets:

- `/files/v2/{locale}/translation/{category}.json`
- `/files/v2/{locale}/translation/{category}.full.json`
- `/files/v2/{locale}/translation/eventStory/event_{eventId}.json`
- `/files/v2/data/search-index.json` and `/files/v2/en-US/data/search-index.json`, retaining `n`/`cn` and adding optional `en`
- Published-only lyrics index/detail files under `/files/translation/lyrics/` and each locale's `/files/v2/{locale}/translation/lyrics/`
- Card-story and area-talk files, `zh-CN` at `/files/translation/cardStory/card_{cardId}.json` and `/files/translation/areaTalk/group_{n}.json`, `en-US` at `/files/v2/en-US/translation/cardStory/card_{cardId}.json` and `/files/v2/en-US/translation/areaTalk/group_{n}.json`, with no `v2/zh-CN` or `v2/ja-JP` mirror

Supported locales are exactly `ja-JP`, `zh-CN`, and `en-US`. `ja-JP` is source-only, and `en-US` is stored independently and is never changed by CN sync or AI translation. Chinese search output remains the compact `{id,n,g,c?,cn?}` schema.

The flat categories are `model.SupportedCategories`, in that order. `gachaInfo`, listed right after `gacha`, carries the fields `summary`, `bubbleText`, and `description`, paired by gacha ID from `gachas.json` `gachaInformation`. Its keys are the exact Japanese masterdata text with line breaks and surrounding whitespace preserved, never trimmed, so consumers look them up with the untrimmed strings. It is published like every other category at `/files/translation/gachaInfo.json`, `/files/translation/gachaInfo.full.json`, and the `v2/{locale}` mirrors.

A card-story file holds one card (`card_{cardId}`); an area-talk file holds every area talk whose JP actionSet ID divided by 100 (integer division) is `n`. Each file is `{meta:{source, version:"1", last_updated}, episodes:{<key>:{scenarioId, title, source, talkData:{<Japanese line key>: <translation>}}}}`, marshalled with two-space indentation and no HTML escaping (`TestSideStoryFilesJSONBytes`). Card episode keys are `"1"` and `"2"`; area episode keys are scenarioIds ordered by actionSet ID. `talkData` holds the translated body and speaker lines in script order and `title` the translated episode title or `""`. The per-episode `source` and the file's `meta.source` are `official_cn` or `official_en` when every translated line, the title included, came from the official server, `human` when any is human, and `llm` otherwise; `meta.last_updated` is the newest write in Unix seconds. A file exists only while at least one body or speaker line has non-empty text. A side-story PUT, AI run, or refresh republishes or withdraws that story's file before answering (`RebuildSideStory`, `TestRebuildSideStoryRepublishesAndWithdrawsOneFile`), and a full rebuild already running at that moment keeps the result: a file first published during it stays published and a file withdrawn during it stays withdrawn (`TestFullRebuildKeepsASideStoryFileFirstPublishedDuringIt`, `TestFullRebuildDoesNotRestoreASideStoryFileWithdrawnDuringIt`). Every full rebuild projects both locales (`TestFullRebuildServesSideStoriesInZhCNAndEnUSOnly`), and the files take the ordinary cache policy below. The legacy backup layout written by `WriteAllContext` carries no side-story file (`TestWriteAllContextLeavesSideStoriesOut`).

Cache and revalidation policy, applied per asset key:

| Asset | `Cache-Control` | Other headers |
| --- | --- | --- |
| Lyrics index and detail | `public, max-age=15, must-revalidate` | strong `ETag`, `Access-Control-Allow-Origin: *` |
| Every other public asset | `public, max-age=300, stale-while-revalidate=3600` | strong `ETag`, `Access-Control-Allow-Origin: *` |

The lyrics pair drops `stale-while-revalidate` on purpose: index and detail are read as one consistent pair and expire on independent timers, so a long TTL would let an edge node answer with a detail that predates the index publication it is validated against. The `ETag` is a strong quoted digest of the exact bytes; `If-None-Match` returns `304`. `GET` and `HEAD` are the only accepted methods, and the permissive CORS header is repeated on `404` and `405` responses so a cross-origin caller reads the status instead of an opaque failure. During drain every public response becomes an observable, logged, CORS-enabled `503`.

Lyrics assets rebuild as one set; a malformed publication preserves the complete previous set rather than exposing a partial index/detail update. The standalone production image embeds the accepted public-only v3 runtime bundle `server/internal/publiclyricsbundle/public-v3.tar.gz` as the reviewed immutable base. It is a self-describing closed inventory with bidirectional 1-to-1 completeness containing only `index.json` and `music_<id>.json`: no manifest, receipt, producer SQLite database, recovery evidence, or private input. Its archive SHA-256 and every count are pinned once in `contracts/public-lyrics/baseline.json`, which `scripts/verify-public-lyrics-baseline.py` checks the committed artifact against; this document deliberately restates neither.

On every files-service projection rebuild the database-backed lyrics projection overlays that bundle: a database publication in state `complete` or `game_only` with a revision greater than the bundle entry, a publication for a music ID absent from the bundle, or any newer non-draft publication replaces or adds that index entry, marks the music ID as database-owned, and replaces its detail bytes. The merged index is re-marshalled with the same deterministic generator marshalling and trailing newline and mirrored to all supported `v2/{locale}/translation/lyrics/` paths. Draft or incomplete database states never override a reviewed `complete` or `game_only` bundle entry, and a failed database projection serves the pure bundle bytes. A bundle that fails to load does not block the rebuild: the projection continues from the database alone and reports `degraded` in its status. An explicitly unpublished song is removed from the merged index and from its detail route even when the bundle contains it; unpublish records that withdrawal in `song_lyrics_public_withdrawals` inside the same transaction that deletes the publication row, publish clears it, and content backups carry the markers. `GET /api/catalog/music` reports a song that has a marker as `lyricsWithdrawn: true` and omits the field otherwise. It likewise reports a source-v3 song as `lyricsSourceV3: true` and omits that field otherwise. A source-v3 song has no publication row, so for it `publish` and `unpublish` only clear or record the marker and require the song's current document revision: they answer `200` with the song's unchanged source-v3 rendition document (whose `status` is always `draft`), repeating the current state writes no audit row and requests no rebuild, and a revision mismatch returns `409 revision_conflict` with that document as `current`. A source-v3 rendition save does not clear a withdrawal; `PUT /api/editor/v1/lyrics/document` does. The overlay is a runtime publication overlay only: it never replaces or mutates the production SQLite database and is not copied into Git/S3 content backups.

A successful `POST /api/editor/v1/lyrics/publish` or `POST /api/editor/v1/lyrics/unpublish`, a non-`dryRun` `PUT /api/editor/v1/lyrics/document`, a successful `POST /api/editor/v1/lyrics/document/takeover`, a changed source-v3 rendition save, a collaboration checkpoint that changes a source-v3 document, a translation-edition create/clone/rename/set-default mutation, and a `music`/`title` batch each request an immediate rebuild (`PublishNow`), so a publication reaches the public site without waiting for the debounced rebuild. Canonical Public Lyrics v3 JSON Schemas and consumer fixtures for MoeSekai are committed under `contracts/public-lyrics/v3/`; legacy v1 fixtures remain only for backward-compatibility checks.

Raw event scenario snapshots, fetched card-story and area-talk scripts, source notes, license notes, source URL, page/revision/SHA identity, fetch timestamps, editor identity, and draft status are authenticated/private data and never enter legacy or v2 public JSON.

A legacy v1 lyrics detail emits the plural `attributions` only when its source revision URL passes the canonical revision-URL rules the public v3 projection applies (`validPublicV3RevisionURL`: an origin the provider accepts and exactly one `oldid` equal to the stored revision ID); otherwise it carries only the plain `attribution`, because pjsk.moe rejects a whole song whose revision URL is not canonical. For the same reason a legacy v1 song published source-only (no translation credit, proofreading credit, or `attribution`) must also yield a non-empty `attributions` list from its source, or publish returns `422 incomplete_publication`; a v2 detail attributes its source bundle and keeps the earlier source-only rule. The requirement applies when a song is published: a v1 publication already stored under the earlier source-only rule is still served and restored.

## Console And SekaiText APIs

The optional `locale` on `GET /api/categories`, `GET /api/entries`, `PUT /api/editor/v1/entry`, `GET /api/event-stories`, `GET /api/event-story`, and `PUT /api/editor/v1/event-story/update` accepts only the three supported locales. Omitted locale delegates to the exact legacy Chinese code path; explicit `zh-CN` event detail reads use the localized segment projection and its mutations and audit rows commit atomically without changing omitted-locale behavior. Localized event rows expose IDs and source hashes, and every explicit-locale write must echo and validate the full episode/type/key/ID/hash identity or receive a contract error or conflict.

SekaiText-Moe uses three additive authenticated routes:

- `GET /api/category/snapshot?category={category}&locale={locale}` requires an explicit supported locale and returns `{category, locale, revision, fields}` for every source-backed identity in every category field from one SQLite transaction. `revision` is an opaque URL-safe digest; clients must not construct or interpret it.
- `PUT /api/editor/v1/category/batch` accepts `{category, locale, baseRevision, updates, clientId?}`. It rejects a stale complete-category revision or any unknown/duplicate entry identity before writing, then applies all changed entries and their content-minimized audit rows in one transaction. Success returns the full `{category, locale, revision, fields}` snapshot plus `updated`, the exact number of values that differed from the base snapshot rather than the submitted update count. A complete no-op returns `updated: 0` with the unchanged revision; stale revisions return `revision_conflict` with the current snapshot.
- `GET /api/projection/status` returns the last published `generation`, whether a rebuild is `pending`, `lastSuccessAt`, and a sanitized `lastError`. Database persistence is complete when a write returns; public `/files` and `/translation` bytes for that save are rebuilt only after the post-save status reaches a later non-pending generation with an empty `lastError`. `POST /api/projection/publish` requests one immediate full rebuild and returns the same status object.

`PUT /api/editor/v1/entry` without a `response` selector preserves the exact legacy success body `{status:"ok"}` or `{status:"noop"}`. A client may request exactly one `response=correlated-v1`; any other or duplicate selector returns `400`. The negotiated success body contains exactly `status`, `category`, `field`, `key`, `text`, and `source`, plus `locale` only when the request selected a nonblank explicit locale.

`GET /api/event-story/episode-snapshot?eventId={id}&episodeNo={episode}&locale={locale}` is authenticated and requires an explicit supported locale. One SQLite read transaction returns event/episode/locale identity, an opaque revision covering scenario SHA plus segment identity/source hash/text/source/revision, the localized episode segments, and `scenario` with `{scenarioId,fileName,sha256,parserVersion,rawJson,sourceTalks}`. Parser version 1 follows the public SekaiText Next JSON loader order for TalkData, close-window blanks, effect types 8/18/23 and trailing-blank removal, and exposes `talkDataIndex` so body/speaker segment positions map to `i*2`/`i*2+1`.

Read-only console endpoints and the operational probes answer write methods with `405` and `Allow: GET, HEAD`. Unknown `/api/` paths return the JSON `404` contract instead of falling through to the static console. JSON request bodies are capped at 8 MiB and reject unknown fields, trailing second values, and duplicate object keys at every nesting level. Editor mutations accept only the closed translation source vocabulary `cn`, `human`, `pinned`, `llm`, and `unknown`.

## Card Stories And Area Talk

Card side stories (`kind` `card`, story ID the card ID, episodes `1` and `2`) and area talk (`kind` `area`, story ID the scenarioId, episode `1`) are translated into `zh-CN` and `en-US`; the Japanese script is the read-only source. Lines are keyed per episode by the trimmed Japanese text: one title line at position -1, and the body and speaker of TalkData index i at positions 2i and 2i+1. Sources are `official` (written only by the backfill from the CN and EN servers' scripts), `llm`, and `human`, and every write increments the line's `revision`. Section 8 of `contracts/editor-api/README.md` is the agent guide with one worked example per route. The routes are Go method patterns, so any other method answers the JSON `404` (`TestSideStoryRoutesAreMethodScoped`):

- `GET /api/editor/v1/stories?kind=&locale=&status=` (authenticated) lists one kind with line counts, `sourceCounts`, `primarySource`, and `status` (`pending`, `untranslated`, `partial`, `translated`).
- `GET /api/editor/v1/story/{kind}/{id}?locale=` (authenticated) returns every episode with its JP fetch and CN/EN import state (`pending`, `imported`, `absent`, `mismatch`, `error`) and every line.
- `PUT /api/editor/v1/story/{kind}/{id}/{episode}` (authenticated, `strictContentMutation`) takes `{locale?, lines:[{jp, text, source?, expectedRevision?}], clientId?}` with 1-2000 distinct lines, text of at most 16384 bytes of UTF-8 without NUL, and source `human` (the default) or `llm`. It is all or nothing: unknown line keys answer `422 unknown_lines` with `current.lines`, stale `expectedRevision` values answer `409 revision_conflict` with `current.conflicts` (`jp`, `expectedRevision`, `currentRevision`, `currentText`, `currentSource`), and nothing is written (`TestUpdateSideStoryLinesIsAllOrNothing`). Success is `200 {status:"ok", kind, id, episode, locale, updated, unchanged, lines}`; when `updated` is positive the story's public file is rebuilt, `NotifyChange` runs, and `sidestory.updated` is broadcast (`TestSideStoryUpdateWritesPublishesAndReportsConflicts`).
- `GET /api/editor/v1/story/{kind}/{id}/{episode}/snapshot?locale=` (authenticated, explicit locale) fetches the live JP script, requires its SHA-256 to equal the stored `scriptSha256`, and returns `{kind, id, episode, locale, revision, segments, scenario}` in the event-snapshot layout the console TXT importer reads; `409 script_not_fetched`, `409 script_changed`, and `502 upstream_unavailable` refuse it (`TestSideStorySnapshotSatisfiesTheConsoleImporter`, `TestSideStorySnapshotRejectsMissingOrChangedScripts`).
- `POST /api/editor/v1/story/{kind}/{id}/ai` (admin) `{locale?, episode?, provider?, clientId?}` runs the producer job `ai-side-story` synchronously, fills lines that have no row or an empty non-human row with `llm` text without overwriting a line edited after its target was listed, and answers `{translated, remaining}` (`TestSideStoryAITranslationsOnlyFillLinesUnchangedSinceTheirTargets`).
- `POST /api/editor/v1/story/{kind}/{id}/refresh` (admin) `{clientId?}` fetches and imports the JP, CN, and EN scripts of every episode at once and answers `{episodes:[{kind, id, key, fetched, scriptChanged, cnState, enState, officialWritten, droppedHumanLines, error?}]}` (`TestRefreshSideStoryFetchesEveryLocaleNow`).
- `GET /api/editor/v1/stories/sync` (authenticated) answers `{state, totals}`; `POST /api/editor/v1/stories/sync` (admin) `{refreshCatalog?}` wakes one round and answers `202 {started, state}`, or `409 backfill_disabled` while the backfill is off (`TestSideStoryBackfillRoutes`).

Snapshot, AI, refresh, and both sync routes answer `503 side_story_unavailable` when no runner is attached (`TestSideStoryRoutesWithoutARunnerAnswerUnavailable`). Runner errors map to `404 not_found`, `409 already_running` (a translate job or producer is running), `503 draining`, and otherwise `502 upstream_unavailable` for refresh and snapshot or `500 internal_error` for AI. Refresh and AI take their own locks; the PUT is the only strict content mutation.

`translator.SideStoryBackfill` runs in the server process while `SIDE_STORY_BACKFILL_ENABLED` is not false and the `side_story_backfill.enabled` setting is not false (unset means on; it is checked every round, so an admin can pause and resume it without a restart). The legacy `scheduler.enabled` switch, which starts the CN version watcher and its event-story auto AI, does not gate it (`TestSideStoryBackfillRunsOnlyWhileItsSettingAndEnvAllowIt`). It is not a producer and never calls an LLM. A round is deferred while a producer runs; otherwise it refreshes the catalog when due (the first round, after 6 hours, when `upstream.state.last_data_version` changes, on `refreshCatalog`, or after a content restore; a failed refresh retries after 10 minutes), fetches at most the batch of due episodes with the request delay between upstream requests, and applies them five episodes at a time under editor admission and the shared content lock (`TestSideStoryBackfillDefersWritesWhileAProducerRuns`). Official CN and EN text pairs with the JP script by TalkData index. A different TalkData length marks that locale `mismatch` and writes nothing. The asset path identifies a script; its `ScenarioId` field is only a label and is not compared, because real JP and CN scripts carry values such as `016048_rui01 のコピー` or `★4冬弥・泉_前半`. An official script that repeats more than half of the kana-bearing Japanese bodies, a mirror still serving the Japanese placeholder of a newly listed script, also writes nothing but keeps the locale `pending` with `lastError` `zh-CN: official script repeats the Japanese text` or `en-US: official script repeats the Japanese text` and is retried like a 404 (`TestApplySideStoryOfficialImportRejectsMismatchedScriptsAndRetriesAMirroredOne`). A 404 for a listed asset path keeps the locale `pending` with `lastError` `zh-CN: not found` or `en-US: not found` and retries it 24 hours later without counting an attempt; a transient error also keeps it `pending` under the episode backoff, and that earlier retry wins when both occur. When the JP script changes under an earlier import, a locale with an asset path that was not fetched in the same call goes back to `pending` for the next round, even when the other locale 404s; a transient error in the other locale still sets its backoff. A catalog refresh that changes a CN or EN asset path and so makes the locale `pending` also resets the episode's attempts, next attempt time, and last error, so the new path is fetched next round rather than after the old path's 404 retry (`TestApplySideStoryRequeueAndANewAssetPathOutrankAnother404`). `absent` only means that the server's masterdata lists no asset path for the episode (`TestApplySideStoryOfficial404StaysPendingAndRetriesADayLater`, `TestSideStoryBackfillRetriesAMirrorServingJapaneseAndA404ADayLater`). The official write inserts a missing row as `official` revision 1 by `sync`, replaces an `official` or `llm` row whose text differs, and never touches a `human` row (`TestSideStoryBackfillKeepsHumanRowsAndRefreshesTheCatalogOnDataVersionAndAge`). Transient JP fetch failures back off from 10 minutes, doubling up to 24 hours; other JP failures, a 404 included, retry after 24 hours (`TestSideStoryBackoffDoublesFromTenMinutesUpToADay`). A round that wrote anything, or whose catalog refresh reports a non-zero `newStories`, `newEpisodes`, `officialRequeued`, `officialTitlesWritten`, or `titlesReplaced`, requests the debounced rebuild and broadcasts `sidestory.sync` with `{detail, current, total}`.

`SyncSideStoryCatalogContext` returns `SideStoryCatalogResult`, which counts `officialTitlesWritten` (official title rows inserted or replaced), `titlesReplaced` (title lines replaced after a JP title change), and `droppedHumanTitles` (human rows deleted with them). When an episode's JP title changes, the old title line is deleted with every translation of it, which counts as a change even when only official rows went; when human rows were among them, the backfill logs `[side-story] <kind> catalog: changed JP episode titles deleted <N> human title translation(s)` once per kind (`TestSyncSideStoryCatalogWritesOfficialTitlesUnderTheOfficialWriteRule`, `TestSideStoryBackfillRebuildsOnCatalogTitleChangesAndLogsDroppedHumanTitles`). After a successful content restore, `afterContentRestore` retires the collaboration sessions and calls `TriggerSideStoryBackfill(true)`. The restore still holds the producer gate, so the refresh may wait one round, at most `SIDE_STORY_BACKFILL_INTERVAL_MS`; nothing runs while the backfill is disabled (`TestAfterContentRestoreRefreshesTheSideStoryCatalog`).

The debounced rebuild waits `FILES_REBUILD_DEBOUNCE_MS` (default 300000, accepted 100-86400000; an invalid value stops startup) after the latest change notification, but never more than two windows after its wait began, so backfill rounds that write every minute cannot hold public files back (`TestDebouncedWriteWaitsOneWindow`, `TestSteadyWritesStillPublishWithinTwoDebounceWindows`).

The backfill environment is validated on every start, and an invalid value stops startup with `side story backfill configuration` (`TestSideStoryBackfillConfigurationDefaultsAndIsStrict`):

| Variable | Default | Accepted |
| --- | --- | --- |
| `SIDE_STORY_BACKFILL_ENABLED` | `true` when unset or empty | `strconv.ParseBool` values |
| `SIDE_STORY_BACKFILL_INTERVAL_MS` | `60000` | 1000-86400000 |
| `SIDE_STORY_BACKFILL_BATCH` | `30` | canonical integer 1-500 |
| `SIDE_STORY_BACKFILL_REQUEST_DELAY_MS` | `1000` | 100-60000 |

Six upstream settings are seeded once from their environment variables like the other `upstream.*` settings, are editable through `/api/admin/settings`, and pass `validateUpstreamURLSetting` in production; an empty value uses the default (`TestSideStorySourcesDefaultToTheStartappMirrorsAndFollowOverrides`, `TestSeedConfigFromEnvSeedsTheSideStorySourceBases`):

The JP and CN catalogs read `cards.json`, `cardEpisodes.json`, and `actionSets.json` (and JP `areas.json`) through the existing `upstream.jp_masterdata_url` and `upstream.cn_masterdata_url` chains; the EN catalog reads `cardEpisodes.json` and `actionSets.json` through the EN keys above. Below each script base the paths are `character/member/<bundle>/<scenarioId>.json` for JP and CN cards, `character/member_scenario/<bundle>/<scenarioId>.json` for EN cards, and `scenario/actionset/group<actionSetId/100>/<scenarioId>.json` for area talk, each server using its own bundle and actionSet ID (`TestBuildSideStoryCardCatalogUsesEachServersBundleAndPath`, `TestBuildSideStoryAreaCatalogComputesEachServersGroupFromItsOwnID`).

## Single-Instance Editor Gate

The server process owns one writer-preferred editor gate. `GET /api/editor-gate/status` requires JWT authentication, is `Cache-Control: no-store`, and returns exactly version 1 `{version, instanceId, revision, generation, completedGeneration, running, lastRun}`. `instanceId` is a random 32-byte base64url value generated for each process start. Producer start increments `generation` and `revision` and publishes `running=true` before waiting for existing editors; completion, including failed jobs, sets `completedGeneration=generation`, increments `revision`, records an RFC3339 completion time, clears `running`, and releases waiters. Therefore `completedGeneration <= generation`. An `/sse` connection receives the current `gate.status` as its first frame, so a freshly opened tab knows the writable state without polling.

Every content write goes through the producer-aware routes:

- `PUT /api/editor/v1/entry`
- `PUT /api/editor/v1/category/batch`
- `PUT /api/editor/v1/event-story/update`
- `POST /api/editor/v1/event-story/promote-human`
- `PUT /api/editor/v1/story/{kind}/{id}/{episode}`
- `PUT /api/editor/v1/lyrics/save`
- `PUT /api/editor/v1/lyrics/document`
- `POST /api/editor/v1/lyrics/document/takeover`
- `POST /api/editor/v1/lyrics/translation-editions`
- `POST /api/editor/v1/lyrics/publish`
- `POST /api/editor/v1/lyrics/unpublish`
- `POST /api/editor/v1/lyrics/{musicId}/collab-ticket` and `POST /api/editor/v1/lyrics/{musicId}/checkpoint`
- `POST /api/editor/v1/admin/lyrics-source-reviews/import`
- `POST /api/editor/v1/backup/push`

`X-Moe-Loaded-Producer-State: <instanceId>:<revision>:<completedGeneration>` is optional on the content routes (every route above except `collab-ticket` and `backup/push`). Without it a content write is admitted like the lenient `contentMutation`: it takes editor admission and the shared content lock, and a running producer returns `409` immediately. When the header is sent it must be exactly one revision-bound value taken from the status loaded with the edited document: a duplicate or malformed/base64/non-canonical/out-of-safe-range value returns `400`; an active producer, stale revision, stale completed generation, or process-restart instance mismatch returns `409` with the exact current producer status object. `POST /api/editor/v1/lyrics/{musicId}/collab-ticket` and `POST /api/editor/v1/backup/push` still require the header and return `428` without it. Validation and shared editor acquisition are atomic, and the atomically accepted producer status is carried in request context rather than reacquired inside handlers.

Three unversioned paths are mounted again for agent scripts: `PUT /api/entry`, `PUT /api/lyrics/save`, and `POST /api/lyrics/publish` use the same auth wrapper and handler as `/api/editor/v1/entry`, `/api/editor/v1/lyrics/save`, and `/api/editor/v1/lyrics/publish`. The other six (`PUT /api/category/batch`, `POST /api/lyrics/translation-editions`, `POST /api/lyrics/unpublish`, `PUT /api/event-story/update`, `POST /api/event-story/promote-human`, `POST /api/backup/push`) still answer the JSON API `404`. `POST /api/admin/lyrics-source-reviews/import` is the one remaining lenient-gate write route, kept for SekaiText-Moe; its strict twin is `POST /api/editor/v1/admin/lyrics-source-reviews/import`. Translation sync, all AI/retry/reorder translation operations, and backup restore are producers; duplicate producers fail immediately instead of waiting. The existing `/api/translate/status` response shape remains unchanged for native proxy compatibility.

Verified lyrics imports are accepted only through `/api/editor/v1/lyrics/save` and its re-mounted alias `/api/lyrics/save`. Source preview is revision-zero/first-save-only, compares exact stopped producer status before and after the external fetch, and rechecks that no lyrics document was created during that fetch before issuing any token. Its grant binds user, music, exact preview, expiry, and the complete producer status, which the save must match: the atomically accepted header value when the header is sent, otherwise the gate status observed when the save runs; claim marks it in flight, correctable draft validation and 5xx outcomes release the exact claim for retry, and success or deterministic invalidation consumes it. Concurrent use of one token permits only one claimant.

## Lyrics Document Route

`PUT /api/editor/v1/lyrics/document` is registered as `RequireAdmin(awaitServedLyrics(strictContentMutation(handleLyricsDocument)))` because it publishes: it replaces the song's lyrics with one source-v3 document plus its `zh-CN` translation editions, which the public projection serves as the v3 detail and, for a song with more than one edition, as the v4 detail. Its strict JSON body is `{musicId, expectedRevision?, source:{url, title?}, translationCredit?, proofreadingCredit?, translationEditions?:[{key, label}], renditions:[{key, kind?, label?, performerIds?, game?, lines:[line], gameLines?:[line], translationCredits?:{translation?, proofreading?}, editionCredits?:{<edition key>:{translation?, proofreading?}}}], dryRun?}` with each line `{ja, zh?, zhEditions?:{<edition key>: zh}, en?, performerIds?, segments?:[{ja, performerIds?}], stanzaBreakBefore?, inGame?}`. `ja` is one line of at most 8192 bytes and `zh` one line of at most 16384 bytes. `ja` carries ruby as `{漢字|かな}` markup, every kanji must be inside it, and `{{` and `}}` write a literal brace; `zh` is stored verbatim. At least one `zh` line is required, and a non-empty `en` is rejected because source-v3 documents do not store English lines. `performerIds` are game character IDs 1-26 or audited external singer IDs, kept in the given order with duplicates dropped, because the main site draws colour gradients and avatars in that order; a line-level list overrides the rendition default, which is the catalog vocal performers for that rendition kind. `segments` (1-100) split a line into runs sung by different performers: their `ja` markups concatenate exactly to the line's `ja`, each is parsed on its own so ruby cannot span two segments, and a segment without `performerIds` sings with the line's performers. `game` is `none` (Full only, the default), `same` (Game identical to Full), `cut` (Game is exactly the Full lines marked `inGame: true`), `independent` (Game is `gameLines`), or `only` (a Game-only rendition: empty `lines`, Game in `gameLines`); a song whose renditions are all Game-only is served as `game_only`. The document credits go to every rendition that has a `zh` line and no `translationCredits` of its own, and at least one of them is required while such a rendition exists; a rendition's `translationCredits` replaces them for that rendition whether or not it is translated, `{}` publishes it uncredited, and at least one rendition must end up credited because the projection serves no uncredited song (`TestPublishLyricsDocumentNeedsDocumentCreditsOnlyForRenditionsWithoutTheirOwn`). The first `translationEditions` entry is the default edition: its text is each line's `zh` and its credits are the document credits or a rendition's `translationCredits`. An omitted or empty list, or exactly `[{"key":"main","label":"默认译本"}]`, means the implicit edition `main`, stored without edition rows. A present list has 1-16 entries whose keys match `^[a-z0-9][a-z0-9._-]{0,127}$`, are unique, and include `main`, with labels of 1-256 bytes after trimming. `zhEditions` (on `lines`, and on the `gameLines` of `independent` and `only` renditions) and `editionCredits` name only declared non-default editions and follow the `zh` and credit limits; a missing key is an empty line or no credit in that edition, and both fields are refused without `translationEditions`. The `zh` and credit requirements above apply to the default edition only, so a non-default edition may be blank. A publish stores what the console edition code stores: the edition rows, `song_lyrics_translation_edition_state` (default key, the new revision, the publish time), per-edition localizations and lines, and the legacy mirror equal to the default edition, so console edition editing continues afterwards (`TestConsoleEditionEditingWorksAfterALyricsDocumentPublish`). `replaceTx` deletes the song's edition state before its source documents, so a song with editions, such as song 682, no longer fails with `FOREIGN KEY constraint failed` (`TestPublishLyricsDocumentReplacesASongWithTranslationEditionState`, `TestPublishLyricsDocumentKeepsTheTranslationEditionsOfSong682`). `source.url` must be a `/wiki/<page>` or `index.php?title=<page>` URL on `vocaloid.fandom.com` or `projectsekai.fandom.com` (both provider `vocaloid_fandom`), `www.sekaipedia.org`, or `moegirl.icu`, with exactly one positive `oldid`; the stored and served revision URL is the canonical `https://<host>/wiki/<page>?oldid=<id>`. `expectedRevision` is required once the song has anything stored or served (a legacy draft or publication, a source document, a recovery ledger item, an embedded bundle entry, or a served detail); only a song with none of them may omit it or send `0` (`TestPublishLyricsDocumentRequiresExpectedRevisionOnlyWhenSomethingIsStoredOrServed`). It must equal `conflictRevision`: the larger of the effective revision (the legacy publication, the embedded bundle, or the edited source-v3 localization when above 1, whichever is newest) and the song's legacy draft revision, because a publish deletes that draft, and at least 1 for an occupied song. The export fills in exactly this value. A publish takes `nextRevision`, one above every legacy, publication, localization, translation-edition, and bundle revision and never below 2.

Success is `200 {dryRun, musicId, revision, publicPath:"/files/translation/lyrics/music_<id>.json", document, changes}`, where `revision` is the new revision and `document` is the public detail object exactly as it will be served, v4 for a song with more than one translation edition and v3 otherwise; `dryRun: true` runs every validation and the same writes as a publish inside the transaction, including the takeover row and `replaceTx`, builds `document` and `changes` from what it wrote, and rolls back. Nothing is committed and no projection rebuild, collaboration reset, or reseed follows, and every failure the publish would hit, including a database error, fails the dry run with the same error (`TestPublishLyricsDocumentDryRunFailsWhereThePublishFails`). `changes` (`LyricsDocumentChanges`) compares the produced detail, both sides read in the request format, with the served detail when the files service has one (`against: "served"`), else with the editable database state (`"database"`), else with nothing (`"nothing"`). It names source, translation edition list (`translationEditions`), rendition, game, effective credit, and per-edition credit (`editionCredits`) changes and, per side, added, removed, and changed lines with the changed fields (`ja`, `ruby`, `segments`, `performers`, `zh`, `zhEditions`, `stanzaBreakBefore`, `inGame`) and their before and after values. `lyricsDocumentAlignLines` anchors identical lines, pairs lines with the same visible text or the same non-empty `zh` between anchors, pairs the remaining lines by position as changed, and lists only the surplus lines as added or removed. An added or removed line summary carries `line`, `ja`, `zh`, `stanzaBreakBefore` (when true), the resolved `performerIds`, `segments` (when the line has several segments or a segment's performers differ from the line's), `inGame` (Full lines of a `cut` rendition), and non-empty `zhEditions` (`TestLyricsDocumentChangeSummariesShowTheStructureOfAddedAndRemovedLines`); counts are complete, at most 200 lines are listed with `truncated` set beyond that, and the unchanged export yields exactly `{"against":"served","changed":false}`. Errors use the contract envelope and are checked in this order, the first failure answering: a missing or non-positive `musicId` returns `422 invalid_lyrics_document` with only `details`; a source URL without exactly one positive `oldid` or on an unsupported host returns `422 source_revision_required`; a music ID not in the catalog returns `404 not_found`; document validation returns `422 invalid_lyrics_document` with every issue at once as `issues:[{rendition, side?, line?, field?, edition?, message}]`, `edition` naming the translation edition of an edition issue (`TestPublishLyricsDocumentLocatesEveryTranslationEditionIssue`), zero-based `line`, markup messages naming the zero-based character index in the line's `ja` markup, and at most 200 issues followed by one `field: "issues"` entry counting the rest (`TestPublishLyricsDocumentReportsEveryIssueInOneBoundedResponse`); a missing `expectedRevision` on an occupied song returns `422 expected_revision_required` with `current:{revision}`; a stale one returns `409 revision_conflict` with `current:{revision}` and the detail `expectedRevision N does not match the current revision M`; a document that yields no servable detail returns `422 invalid_lyrics_document` with only `details`; and a failed database write returns `500 {"error":"internal_error"}`, logged on the server. A publish advances the song's collaboration epoch inside its transaction and then closes every resident collaboration room of that song except the reseeded one. The agent-facing guide is `contracts/editor-api/README.md`.

A song held by the recovery import ledger (`lyrics_recovery_import_items`) is published like any other song. Its first non-`dryRun` publish inserts one `lyrics_recovery_takeovers` row (migration v38) in the same transaction, before the replacement deletes the recovery source document. The row names the superseded ledger item, which is the item owning the current source document or otherwise the song's newest item, and keeps that document's `document_json`, `document_sha256`, `schema_version`, `reason_code`, and `created_at` verbatim; all five are NULL for an item that owned only an availability document. For a superseded schema-3 document, `localizations_json` also keeps every `zh-CN` translation row the replacement deletes: the rendition localizations with their credits and revision, the Full and peer-side translation lines, and the translation edition state, editions, edition localizations, and edition lines, as canonical JSON validated before the insert and on every backup; it is NULL when the document had none. The ledger rows stay unchanged; a dry run inserts the takeover row inside its transaction and rolls it back with the rest, and a refused publish writes none. Once a takeover exists, `resolveLyricsRenditionEditorProvenance` accepts the song's editor-published document, `CatalogMusic` stops reporting the ledger's `lyricsAvailabilityState`, and later publishes take the ordinary path without another row. Until then the editor document of a song whose source document the ledger owns carries `recoveryLedgerOwned: true`, and its source-layer edits answer `source_drift` while translation edits save. The offline recovery public candidates of a taken-over batch (v3, v2 compatibility, and v4) are built from the takeover's verbatim document and its `localizations_json`, so they equal the pre-takeover candidates including `zh` and translation editions (`TestRecoveryPublicCandidatesOfATakenOverTranslatedItemKeepTheLedgerTranslations`, `TestRecoveryPublicCandidatesOfATakenOverItemKeepTheLedgerTranslationEditions`); a superseded legacy v2 item, which carries no `localizations_json`, contributes only its ledger Japanese text at revision 1. The insert trigger requires the row's batch, state, and document digest to match its ledger item, updates are refused, and a delete is allowed only once the ledger item is gone, so rows cascade with their item when content restore deletes the catalog and recovery batches. No API removes a takeover.

`GET /api/editor/v1/lyrics/document?musicId=<id>[&from=served|database]` is registered separately as `RequireAuth(awaitServedLyrics(handleLyricsDocumentExport))`: any authenticated editor may call it, it takes no producer-state header and no content lock, and every other method on the path still reaches the admin registration above. With `from=served`, the default, it reads the detail bytes the files service currently serves for the song (`PublicLyricsDetail`), decodes public version 1, 2, 3, or 4 (a v4 detail contributes every translation edition), and falls back to the database state when the site serves nothing; `from=database` reads the editable database state through `ExportLyricsDocumentFromDatabase`: the song's source-v3 document with every translation edition, withdrawn or not, else its legacy draft. A song with more than the implicit edition exports `translationEditions`, line `zhEditions`, and rendition `editionCredits`, so an unchanged export sent back reproduces the same public detail with every edition (`TestLyricsDocumentExportOfAMultiEditionSongRoundTripsToTheSameV4Detail`, `TestExportLyricsDocumentCarriesEveryTranslationEditionOfAV4Detail`); a song whose only edition is a renamed `main` is served as v3, which has no edition label, so when the stored song matches the served one the served export and the `changes` baseline take `translationEditions` from the database (`TestLyricsDocumentExportKeepsTheLabelOfARenamedOnlyEdition`). It answers `200 {musicId, from, servedVersion, servedRevision, document, warnings}`, where `from` names the source actually read and `servedVersion` and `servedRevision` are 0 when nothing is served. `document` is a request the PUT accepts, with `expectedRevision` set to `conflictRevision`; `warnings` is always an array of `{code, rendition?, side?, line?, message}` naming each part of the detail the request cannot carry. `unpublished_draft_replaced` names a legacy draft whose lyrics differ from the served song, whatever its revision, which the PUT would delete; `served_revision_differs` a served revision other than the effective revision, because either the projection has not rebuilt yet or the source-v3 translation saved at that revision has no translation or proofreading credit on any rendition, which the projection never serves; `withdrawn_republished` a withdrawn song the PUT would publish again; and `credit_missing` a detail with no credited rendition, which the PUT rejects. A non-positive `musicId` or a `from` other than `served` or `database` returns `400 invalid_query`; a song with nothing served and nothing editable returns `404 not_found` whose `current:{revision}` names the `expectedRevision` a creating PUT must send; and a server without a files service returns `503 projection_unavailable`. `TestLyricsDocumentExportRoundTripsTheEmbeddedBundle` exports every embedded-bundle song, publishes the export through PUT, and requires that only the codes in `lyricsDocumentRoundTripPermittedWarnings` occur, that every difference outside a commented allowlist is matched by a warning on the same rendition, that no line differs in text, segments, per-segment performer order, ruby, or trailing performers, that segments with several performers keep their boundaries, that each accepted export reports no `changes`, and that re-exporting the published song yields the same request without warnings.

`POST /api/editor/v1/lyrics/document/takeover` is registered as `RequireAdmin(awaitServedLyrics(strictContentMutation(handleLyricsDocumentTakeover)))` with the strict body `{musicId, expectedRevision}`. `TakeOverLyricsDocument` exports the served detail as GET does and publishes that request as PUT does, so a song served from the recovery ledger, a legacy publication, or the embedded bundle becomes an editor document with unchanged public lyrics. A song the site does not serve returns `404 not_found`; otherwise the PUT checks apply in the PUT order, including `422 expected_revision_required` and `409 revision_conflict`, and a refused takeover writes nothing. Success is the PUT result plus `warnings`, the export warnings as an array (`TestLyricsDocumentTakeoverRoutePublishesTheServedSongAsADocument`, `TestTakeOverLyricsDocumentMakesAServedLedgerSongAnEditorDocument`); a song with several translation editions keeps all of them (`TestTakeOverLyricsDocumentKeepsTheEditionsOfARecoveryLedgerSong`).

The public-file rebuild after a publish is asynchronous (`PublishNow` signals the files worker), so for a moment after any lyrics publish the site still serves the replaced detail, while the database already holds the new revision. An export read then would carry the old lyrics with the new `expectedRevision`, and a PUT of it would silently revert the publish. `awaitServedLyrics` therefore runs before the three document handlers, outside every lock: when a publication is pending it calls `filesvc.Service.AwaitPublished`, which publishes a request still inside its debounce window at once and waits, for at most 10 seconds, until every publication requested before the call is published. Past that bound the handler runs anyway, and a stale served detail still carries `served_revision_differs` (`TestLyricsDocumentExportWaitsForAPendingPublication`, `TestAwaitPublishedPublishesADebouncedRequestAtOnce`).

`POST /api/editor/v1/lyrics/document/ruby` is registered as `RequireAuth(handleLyricsDocumentRuby)`: it reads and writes no song, so any authenticated editor may call it without a producer-state header or content lock. Its strict body is `{lines:[ja markup]}` with 1-2000 single-line markups of at most 8192 bytes each; anything else returns `400 invalid_request` with `details`. It answers `200 {generator, lines:[{ja, suggested:[{character, text, reading}], problems}]}`, one entry per request line: `SuggestLyricsDocumentRuby` tokenizes the visible text with the Kagome/IPADIC dictionary that source import uses (`lyricssource.SuggestRubySpans`, which keeps an unreadable token as plain text instead of failing the line), writes a word-level `{kanji|reading}` for every dictionary word whose kanji carry no ruby and do not overlap a written ruby, and keeps every written ruby and escaped brace as written. `character` is the index of the added ruby's `{` in the returned `ja`, and `problems` are the `ja` problems a PUT would still report for it; markup with any other `ja` problem is returned unchanged with its problems (`TestSuggestLyricsDocumentRubyFillsOnlyKanjiWithoutRuby`, `TestLyricsDocumentRubyRouteSuggestsReadingsForAnySignedInUser`). The readings are dictionary readings for the caller to check against the source; nothing records them as source evidence.

## Lyrics Collaboration

Lyrics draft collaboration uses browser `yjs`/`y-websocket` and `github.com/reearth/ygo` in the existing Go process; no Node.js, V8, or separately deployed collaboration service is part of the runtime contract. The authenticated entry point is exactly `POST /api/editor/v1/lyrics/{musicId}/collab-ticket`, whose closed optional body is absent, `{}`, or `{musicId}` and which returns exactly `{ticket,room,expiresAt}`. A ticket is random, process-local, expires after 45 seconds, is consumed by the first attempted upgrade, and is bound to the authenticated username, role and token generation, music ID, collaboration epoch, and the atomically accepted stopped editor-gate snapshot. The WebSocket endpoint is exactly `/yjs/lyrics/{musicId}?ticket=<one-time-ticket>`; a long-lived JWT must never appear in that URL, and the server rewrites the room to the internal identity `lyrics-{musicId}-e{epoch}`.

Each document has the root map `lyrics` and `schemaVersion: 1` with nested `Y.Map`/`Y.Array`/`Y.Text`; an opaque whole-document JSON string is not conforming. Items in `segments` and `ruby` carry collaboration-only `__yjsId`, `__yjsGeneration`, and optional `__yjsOrigin` fields that materialization strips. Mixed legacy/identified items, incomplete metadata, duplicate IDs, or multiple generations derived from the same origin are a closed structural conflict: the browser stops automatic reconnect and keeps the authoritative REST document read-only, and server checkpoint materialization returns `invalid_collaboration_document`.

`POST /api/editor/v1/lyrics/{musicId}/checkpoint` is the only materialization operation. It revalidates the editor gate and the authoritative base revision/hash and commits the authoritative lyrics mutation, collaboration snapshot/base envelope, and checkpoint ledger in one SQLite transaction. A legacy lyrics checkpoint only requires the same kind and music ID and otherwise follows the ordinary save rules, so a saved revision may change provenance, line structure, and Japanese text; a source-v3 checkpoint still rejects a changed line count, line ID, order, or Japanese text with `source_drift`. `lyrics_collab_documents.epoch` is a monotonic database fencing generation checked in the same transaction as every persisted update; backup restore fences every room epoch in the restore transaction, and the ledger deliberately has no cascading catalog foreign key so catalog delete/reinsert cannot reset an epoch. SQLite's normalized lyrics and source-v3 tables remain authoritative for API reads, content backup, restore, audit, and public projection.

Ygo limits are mandatory nonzero code-owned production defaults: 50 global connections, 10 peers per room, 256 rooms, 128 resident rooms, an 8 MiB raw update and merged-document cap, an 8 MiB + 64 KiB WebSocket message cap for Yjs framing overhead, 100,000 pending CRDT items, 20 messages/second with burst 40, a 256-message peer write queue, 256 KiB and 256 clients of awareness per room, a 10-second handshake, 90-second awareness expiry, five-minute idle-room eviction, and a one-second maximum persistence-coalescing wait, compacting after every 100 successful flushes. They are not environment-configurable in this release.

## Lyrics Sources And Private Review

An ordinary save may omit `sourceUrl` or store any valid external reference, including a URL on the managed Vocaloid Wiki origin, and a later revision may change the source reference, line IDs and order, and Japanese text. Provenance is all-or-nothing: `sourcePageId`, `sourceRevisionId`, `sourceSha1`, `sourceFetchedAt`, and `sourceUrl` are supplied together, a managed-origin URL must name that revision, and every provenance-bearing save and restore requires an exact lowercase 40-hex source SHA1. The verified preview/import path remains first-save-only. Contract errors use sanitized codes including `revision_conflict` (409), `source_drift`, `segment_mismatch`, `invalid_performer`, `incomplete_publication`, and `translation_required` (422); `translation_required` refuses a source-v3 layout or performer edit on a song that has no translated line or credit yet and whose save adds none. Pinned identity establishes consistency with the fetched revision; it does not establish copyright ownership or permission to publish. Public publication requires non-empty operator-authored `attribution`, which together with private `licenseNote` and `sourceNote` is operator metadata rather than a verified grant.

Phase 1 discovery and Phase 2 fixed-revision fetching are independently disabled by default. `LYRICS_DISCOVERY_ENABLED=true` seeds `lyrics_discovery.enabled` and `LYRICS_FETCH_REVISION_ENABLED=true` seeds `lyrics_discovery.fetch_revision.enabled`; after the first seed, authenticated settings are authoritative. Only one explicit full target with complete role-bound credits is scanned automatically; game-size siblings are association evidence only, and missing/contradictory version metadata or short/preview/partial/cover/medley signals fail closed into private review. The separately gated fetch worker performs an uncached MediaWiki request by exact revision ID and rejects cross-page, revision, SHA1, title, URL, category, origin, restriction, version, markup, response-size, raw-byte, or extraction drift. Both workers are constructed before but start only after successful TCP bind; shutdown drains admission, cancels active work, waits for both loops, and only then closes SQLite. Lease, job-timeout, idle, retry, and discovery scan timings are bounded environment-configurable milliseconds; invalid ranges fail startup.

The canonical private review endpoints are exactly `GET /api/admin/lyrics-source-reviews`, `GET /api/admin/lyrics-source-reviews/detail?reviewId=`, `PUT /api/admin/lyrics-source-reviews/decision`, `PUT /api/admin/lyrics-source-reviews/candidate-selection`, and `POST /api/admin/lyrics-source-reviews/import`. Every route uses bearer-header `RequireAdmin`, `no-store`, bounded closed DTOs, and expected-version CAS; PUT and POST require `application/json`. Batch success is exactly `{items,replayed}` with every item exactly `{reviewId,state,version}`. Actor-scoped idempotency keys are shared across single/candidate decision rows and batch parent rows: only the same request kind and exact payload replays, while cross-kind/payload reuse or any derived batch-child collision returns deterministic `idempotency_conflict` before mutation. Raw wikitext and internal artifact/analysis/extracted-line hashes never enter these APIs, lists, logs, content SSE, public files, or shared Git/S3 content backup.

The import route's closed request is `{reviewId}`. It revalidates approved review/gate state, pinned policy versions, the complete current catalog target grouping and fingerprints, immutable source identity, structured extraction digest, ruby/segment invariants, and performer projection in the first-save transaction, then creates revision 1 as a private editable draft with empty `zh-CN`/`en-US` translations and does not publish it. Exact replay is idempotent with `changed:false`; a nonidentical existing document returns `lyrics_already_saved`.

Sekaipedia's music-ID-to-page-title bindings and song-scoped contributor aliases are database configuration, not compiled constants: administrators edit them under 管理设置 → 歌词来源映射（Sekaipedia） through `GET /api/admin/lyrics-providers/sekaipedia/targets` and `PUT`/`DELETE /api/admin/lyrics-providers/sekaipedia/targets/{musicId}`. A mutation is stored only after the provider registry accepts the whole would-be map, and the running server then installs the new registry without a restart. The fixed `List of songs` index revision pin stays compiled into the binary.

38. `lyrics_recovery_takeovers` creates only the table `lyrics_recovery_takeovers`, its index `idx_lyrics_recovery_takeovers_item`, and the RAISE-only triggers `lyrics_recovery_takeovers_item_insert`, `lyrics_recovery_takeovers_immutable_update`, and `lyrics_recovery_takeovers_immutable_delete`. A row, keyed by `music_id`, records the recovery ledger item a whole-song document publish superseded together with that item's source document verbatim and, in the nullable `localizations_json` column, the superseded document's translations; a CHECK admits that column only with `schema_version` 3, as a JSON object whose `localizations` array is non-empty. Its foreign key to `lyrics_recovery_import_items` cascades on delete. No existing table or row changes.
39. `side_stories` creates only the tables `side_stories`, `side_story_episodes`, `side_story_lines`, and `side_story_line_localizations` and the index `idx_side_story_line_localizations_locale`. Stories are keyed by `(kind, story_id)`; episodes add `episode_key` with the JP/CN/EN asset paths, `script_sha256`, `jp_refetch`, `cn_state`, `en_state`, and the retry fields; lines add the trimmed `jp_key` with `role` and `position`; localizations add `locale` (`zh-CN` or `en-US`) with `text`, `source` (`official`, `llm`, `human`), a positive `revision`, `updated_by`, and `updated_at`. CHECK constraints pin the identity formats and state vocabularies, every foreign key cascades from story to localization, and no raw script is stored. No existing table or row changes (`TestMigrationV39UpgradesAV38DatabaseByOnlyAddingSideStoryTables`, `TestV39SideStoryConstraintsRejectInvalidRows`, `TestV39SideStoryRowsCascadeFromStoryToLocalization`).

The song-682 migrations v32-v34 were reissued while rolling out, so `historicalMigrationChecksums` accepts exactly their recorded digests in addition to the current SQL checksum; no other migration may drift. Migrations after v34 are SQL-only and must not write the lyrics/catalog content tables: `TestMigrationsAfterV34MustNotMutateContentTables` refuses any later migration that carries a Go hook or that inserts into, updates, deletes from, or drops those tables. v36 still inserts its seed rows, but only into the two provider-target tables it creates. Two exceptions are declared. v37's rebuild of `song_lyrics_source_artifacts`, which the test's prefix match treats as a content table, may carry only the column-for-column `INSERT ... SELECT` from `song_lyrics_source_artifacts_v36` and the drop of that predecessor, and `TestMigrationV37RebuildsSongLyricsSourceArtifactsVerbatim` compares every table's rows and every schema object before and after. v38 is create-only: the `lyrics_recovery_` prefix makes the recovery ledger and its takeover table content tables, and the test accepts from v38 only the `CREATE TABLE`, `CREATE INDEX`, and RAISE-only `BEFORE` triggers of `lyrics_recovery_takeovers` (`TestCreateOnlyStatementAllowsOnlyTheNamedTableIndexAndRaiseTriggers`); `TestMigrationV38OnlyCreatesTheTakeoverTable` checks that it adds exactly that table, index, and three triggers and leaves every table's rows unchanged. v39 is create-only the same way for its four tables and one index.

Before the first pending migration in one startup, file-backed databases receive a verified `*.pre-migration-vN.bak` SQLite backup, where `N` is that first pending version. A multi-version jump therefore produces one recovery point for the pre-upgrade database, not one backup per intermediate migration. Startup also requires the recorded migration history to be a contiguous prefix with matching names/checksums and runs a full `PRAGMA integrity_check` after schema/migrations before returning the database to the server. Migration tests cover idempotent reopen, checksum/gap refusal, injected rollback, backup recovery, legacy writer compatibility, private file modes, old event replacement, explicitly pinned v10-v30 checksums, private-source schema rollback, and the deterministic v19 empty-segment repair plus exact ruby invariant.

Migration v9 requires a single-instance `Recreate` rollout. Before starting the v9 binary, stop the old instance and create a verified full SQLite off-host backup. Do not run old and new writers concurrently and do not roll back an old binary onto a v9 database. When upgrading across v8 and v9 together, restore the verified backup named for the first pending version (for example `*.pre-migration-v8.bak`) or the off-host snapshot as described in `ROLLBACK_RUNBOOK.md`.

## Offline Module Boundary

Every offline operator command and its private packages compile from the nested Go module `server/offline` (`moesekai/server/offline`, which replaces `moesekai/server` with `../`). The production module never requires that module, and `server/production_deps_test.go` asserts that `go list -deps .` for the server binary contains no `moesekai/server/offline/` package. CI runs `go test` and `go vet` separately in `server/` and `server/offline/`. The main module's `cmd/` contains only `migrate`.

`lyrics-stage` encodes catalog contract version 18 in reports/manifests, accepts only immutable standalone runtime snapshots whose migration history is contiguous from v1 and ends between v18 and v39, requires the v18 catalog columns and `catalog-identity-v2` fingerprints, and rejects future runtime schema versions until compatibility is reviewed. `lyrics-import-stage` is never copied into the production image or invoked by the server: it requires absolute manifest/database/backup/receipt paths, the verified backup SHA-256, an audit operator, and `-confirm-local-offline`; it refuses `MOESEKAI_PRODUCTION`, acquires the same single-instance database ownership lock, pins input and database inodes, rejects SQLite sidecars, and reserves the private receipt with `O_EXCL`. Import revalidates the manifest's closed schema/digests, complete current catalog generation, policy/fingerprints/targets/associations, fixed page/revision/SHA1 URL identity, performer mapping, empty translations, and exact ruby/segment structure. Projection accepts only IDs in the runtime's closed game-character performer catalog; when catalog evidence contains only `outside_character` vocals the private draft stores a concrete empty `performerIds` array rather than fabricating a colliding ID, and ordinary publication validation continues to block it. All new drafts and audit rows commit in one transaction; exact existing documents replay, any nonidentical document conflicts, and any item failure rolls back the complete batch. Schema-v2 staged manifests carry each item's actual fixed-revision `source.fetchedAt`, which import writes as `sourceFetchedAt`. `lyrics-import-stage`, `lyrics-recovery-import`, and `lyrics-recovery-public-candidate` require a contiguous v27 through v39 history; v37, v38, and v39 were reviewed as compatible because they change neither the catalog identity nor the recovery inputs, and v40 or later is refused until reviewed (`TestRunRejectsUnreviewedV40RuntimeWithoutCreatingOutput`). `lyrics-preflight` requires a catalog database at exactly v18, and `lyrics-catalog-filter` reads the highest recorded version with neither an upper bound nor a contiguity check. On a runtime that records v38, `lyrics-recovery-import` refuses a new batch that contains an item for a song with a `lyrics_recovery_takeovers` row (`refuseRecoveryItemsForTakenOverSongs`). On every supported runtime it also refuses a new batch that contains an item for a song whose source document the lyrics editor owns (`refuseRecoveryItemsForEditorOwnedSongs`): a document with the all-zero `manifest_batch_sha256` that `PUT /api/editor/v1/lyrics/document`, the takeover route, and migration v32 (song 682) write, or, on a runtime that records v28, a document of an `embedded_lyrics_editor_seed_batches` seed. Both refusals wrap `ErrLyricsRecoveryImportConflict`, name the music ID, and leave the replay of an already imported batch unchanged (`TestNewRecoveryBatchRefusesSongsTakenOverByADocumentPublish`, `TestNewRecoveryBatchRefusesSongsWithEditorOwnedSourceDocuments`). Because a batch must cover the whole catalog, no new batch imports once any song has been published through the document route or taken over, and a database on which migration v32 wrote song 682's document (it does whenever 682 is in the catalog and owns no source document yet) already refuses every new batch.

## Backup And Restore

Git and S3 backups retain the legacy category/event `translations` restore projection, physically archive the SQLite-snapshot public lyrics projection as `translations/lyrics/index.json` and `translations/lyrics/music_<id>.json`, and add `translation-content/manifest.json`. The archived public lyrics bytes must exactly equal the corresponding `PublishedLyricsJSON` bytes from the same SQLite snapshot. Both backup projections are materialized from one SQLite snapshot; manifest schema version 2 checksums and counts multilingual entries, stable event content, catalog/lyrics drafts, source provenance, publication snapshots, and, in `translation-content/side-stories.json`, every row of the four v39 card-story and area-talk tables. Drafts, private provenance, and publication database state remain preserved by `translation-content/lyrics.json` so restore can reconstruct the editable SQLite state. Legacy and additive restore data commit in one transaction, failure rolls everything back, and backups without the additive directory explicitly clear multilingual/lyrics-only state. If the target already contains native Public Lyrics source-v3 documents, application-level content restore replaces them atomically, suspending the source-document delete guards inside the restore transaction and reinstating them before commit. Shared restore preserves all private source rows and supersedes only stale pending review fingerprints. V2 locale projections and search indexes are not archived, and backup push is content backup only — not deployment, static publication, or CDN synchronization. `BackupAll` fails, does not advance `LastBackup`, and does not consume scheduler success when both targets are disabled. An unencrypted Git backup whose staged tree equals the branch tip creates no commit and no push and counts as a successful backup.

`BackupAllContext`, which both `POST /api/editor/v1/backup/push` and the scheduler run, builds one archive for both targets, and `publishGitBackupArtifactContext` replaces the Git branch's tree with that single file: `backup.tar.gz`, or `backup.enc` when `MOESEKAI_BACKUP_ENCRYPTION_KEY` is set (`TestBackupAllUsesOneSnapshotForS3AndGit`, `TestLegacyGitBackupCommitsOnlyEncryptedArtifact`). GitHub rejects a pushed file larger than 100 MiB, so that file must stay below it. The 2026-09-24 upstream probe estimated `side-stories.json` at 173-192 MiB of JSON and 23-26 MiB after gzip, about ±15%, for a total archive of about 66-70 MB.

Artifacts written by the embedded editor seed and by `PUT /api/editor/v1/lyrics/document` cite index evidence whose parent rows in `lyrics_source_index_evidence` are deliberately absent, because neither stores raw provider evidence. Export writes no evidence link for such a reference and restore accepts it; a parent row that is present must still match exactly. Archives and legacy seeds made before `gachaInfo` existed lack both of its files: S3/Git restore, `importer`, and `cmd/migrate` then restore that category as empty, replacing any current `gachaInfo` entries like every restored category, while an archive holding only one of the two files is still an incomplete layout.

`translation-content/side-stories.json` is `{stories, episodes, lines, localizations}` with every column of the four v39 tables in lowerCamelCase, and its manifest count is the sum of the four array lengths. A schema-version-2 manifest must list exactly the four files and a schema-version-1 manifest exactly the original three (`entries.json`, `event-stories.json`, `lyrics.json`); any other file set or version is refused before anything is written (`TestTranslationContentManifestFileSetMatchesItsSchemaVersion`). Restore validates every side-story row (identity, episode key, states, digests, trimmed line keys, role and position, locale, source, positive revision, orphans, duplicates) before its first delete and replaces the four tables inside the same restore transaction as the other content (`TestSideStoryBackupRestoresEveryRowExactly`, `TestSideStoryRestoreRejectsTamperedRowsAndLeavesTheDatabaseUnchanged`). Restoring a schema-version-1 archive, or a legacy archive without the additive directory, empties the four tables, so their card-story and area-talk translations are gone until the backfill, which the restore asks for a catalog refresh, re-imports the official text (`TestRestoreWithoutSideStoriesClearsTheSideStoryTables`, `TestS3RestoreOfSchemaVersion1BackupClearsSideStories`). A binary older than v39 refuses a schema-version-2 archive with `unsupported translation content schemaVersion 2`.

`translation-content/lyrics.json` carries recovery takeovers as the optional `recoveryTakeovers` list, which export writes only from a database that records v38. Each record carries `localizationsJson` when the row has `localizations_json`; restore writes it back byte for byte, and validation (`validateLyricsRecoverySupersededLocalizations`) accepts it only for a superseded schema-3 document, only as the canonical encoding with its rows in primary-key order, and only when those rows satisfy the content backup's rendition-localization and translation-edition rules for that document. Restore inserts takeovers after the availability documents. Validation rejects a takeover whose ledger item is absent, whose item state differs, whose superseded document is present when the item pinned none or absent when it pinned one, or that repeats a song; a superseded document enters the recovery graph as its item's source document, so the ownership, fixed-identity, artifact, and contribution checks still run against it. An archive without the list restores with no takeovers. Restore also validates every archived legacy publication with the rules it was published under, so a v1 publication needs a translation credit or the earlier source-only provenance but not the served `attributions` that new publications require, and a violation rolls back the whole restore. Takeover rows count toward the `lyrics.json` manifest count and the aggregate record limit below.

`translation-content/event-stories.json` additionally contains canonical scenarios; its legacy `count` remains segments + localizations + locale metadata while optional `scenarioCount` validates the new rows. Restore safety limits keep ordinary files at 64 MiB while allowing `translation-content/event-stories.json` up to 512 MiB and `translation-content/side-stories.json` up to 256 MiB (`TestSideStoriesContentFileHasItsOwnSizeLimit`); expanded archives remain bounded at 1 GiB, compressed S3 responses at 256 MiB, and additive content at 2,000,000 aggregate typed records (`TestTranslationContentRecordLimitLeavesRoomForProductionScaleSideStories`).

The content backup deliberately excludes: user tables, password hashes, settings, token generations, audit records, secrets, raw provider payloads, the embedded release bundles, and the two v36 provider-target tables (`lyrics_provider_page_targets` and `lyrics_provider_contributor_aliases`), which are operator configuration rather than translated content. Restoring a backup therefore never rewrites the Sekaipedia map; it is re-seeded by migration and edited through the admin API. Consequently this content backup is not a full database backup: production operations must additionally create full SQLite snapshots with SQLite's online backup API, `.backup`, or `VACUUM INTO`, verify `PRAGMA integrity_check`, encrypt the snapshot, and transfer it to independently controlled off-host storage. Copying only the main `.db` file while WAL writes are active is not a valid backup. Full snapshots must be taken before migration v9 and before rollback-sensitive releases.

## Standalone Image Invariants

Production mode is explicitly enabled with `MOESEKAI_PRODUCTION=true`. The standalone production image both persists that value and replaces the development server with a binary link-stamped as `next-production`, so a deployment-level empty/false/case/whitespace override is rejected instead of disabling production checks. The image also persists `WORKSPACE_MODE=disabled`, the immutable bundled console root `WEB_DIR=/app/web`, `DB_PATH=/data/moesekai.db`, `DATA_DIR=/data`, and exact `TZ=UTC`. `WORKSPACE_WEB_DIR` and `WORKSPACE_MANIFEST_SHA256` must be unset; any missing or non-exact production value fails during `--verify-runtime` before the persistent data path is touched, and the container entrypoint runs that preflight before database ownership/open, upstream validation, or worker construction. Production startup then sets `time.Local = time.UTC`. Literal, decoded, and normalized paths entering the retired `/workspace` return `404 no-store` before preflight and ServeMux, with no console fallback. Runtime identity is `65532:65532` with a read-only root, a writable persistent `/data`, and a bounded `/tmp` tmpfs; one process owns the SQLite location for its lifetime.

Production also requires at least 32 bytes of `MOESEKAI_MASTER_KEY` secret material and at least one initialized admin; a fresh database must receive a valid `ADMIN_PASSWORD` or `TRANSLATOR_ACCOUNTS` bootstrap secret. `editor` and `admin` are the complete role vocabulary. Settings patches reject unknown keys before commit, store every value (secrets included) with surrounding whitespace trimmed so a whitespace-only value clears the setting, environment seeds, which fill only absent keys, are stored trimmed as well (a value that trims to empty seeds nothing), and `backup.daily_hour` accepts only canonical integer strings from `0` through `23`. Publication uses a directory-durable incomplete marker; an unconfirmed post-rename target is removed or rejected by the entrypoint instead of being accepted on restart.

The same binary embeds one private canonical editor seed at `server/internal/embeddedlyricsseed/editor-seed.tar.gz`, whose archive SHA-256 is pinned in `contracts/public-lyrics/baseline.json`. Immediately after SQLite opens and before environment settings or bootstrap accounts may write, startup inspects the live catalog: an empty catalog is explicitly deferred so the existing first-boot bootstrap can initialize it, while every nonempty catalog must match the canonical music IDs, Japanese titles, `catalog-identity-v2` fingerprints, and aggregate digests exactly. One exclusive SQLite transaction then fills only music IDs with no existing legacy draft, source document, recovery availability document, or previously inserted embedded availability ownership; existing ownership is recorded as `preserved_existing` and never overwritten. The batch and item ledger is immutable, restart replay validates the exact batch and reports zero new changes, and any catalog mismatch rolls back without a seed batch or item. The one sanctioned ledger change is made by `PUT /api/editor/v1/lyrics/document`: when it replaces a seed-inserted song it re-records that song's `inserted` items as `preserved_existing` inside its transaction, because replay compares `inserted` items with the seed's own document and requires only continued database ownership for preserved ones. The archive contains no raw recovery evidence, provider payload, producer database, credentials, users, settings, ordinary translations, stories, reviews, or publications, and is never served by `/files` or `/translation`.

`/readyz` requires SQLite, at least one successfully published initial public projection with no known latest-generation failure, and a live or validated cached search index; `/healthz` remains independent liveness. Initial generation runs asynchronously after the listener is acquired, and every failed requested publication retries with bounded exponential backoff until the latest requested generation publishes or shutdown cancels the worker. On drain, only exact `GET`/`HEAD` `/healthz` and `/readyz` remain admitted. One configurable total shutdown budget covers a short HTTP drain, cancellation, forced HTTP close, and all tracked worker/request joins before SQLite closes; if a noncancelable filesystem or SQLite critical section exceeds it, a watchdog logs a critical fail-closed message and exits.

JWTs carry a persisted per-user token generation and are accepted only while the user still exists and the current database role and generation match. Password changes, role changes, and deletion immediately reject previously issued tokens. Public setup and login attempts are bounded in memory by both the normalized account and the socket `RemoteAddr`; forwarding headers are intentionally ignored. Editors may proofread individual entries, event lines, card-story and area-talk lines, and lyrics drafts; CN sync, every AI trigger, event retry/reorder/promote, side-story refresh and backfill trigger, backup push/restore, user/settings/upstream administration, provider-target administration, and lyrics publication are admin-only.

Image build, digest pinning, signing, and the manual publication workflow are defined in `STANDALONE_RELEASE.md`; production rollback is defined in `ROLLBACK_RUNBOOK.md`.
