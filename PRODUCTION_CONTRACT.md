# Locale And Lyrics Production Contract

This document records what the pjsk.moe main site and production operators depend on: the public file paths and their JSON shapes, the cache/ETag/CORS policy, the strict editor gate, the applied migration list, the offline module boundary, backup scope, and the standalone image invariants. `LEGACY_BASELINE.md` remains authoritative for requests without an explicit locale and for all existing public bytes.

## Public Files

Legacy `/files/translation/*` and `/translation/*` generation, ETags, CORS, and cache policy are unchanged. `/translation/<suffix>` is a backward-compatible alias for `/files/translation/<suffix>`; `/translation/lyrics` and `/translation/lyrics/` are literal aliases for `/translation/lyrics/index.json`.

Additive assets:

- `/files/v2/{locale}/translation/{category}.json`
- `/files/v2/{locale}/translation/{category}.full.json`
- `/files/v2/{locale}/translation/eventStory/event_{eventId}.json`
- `/files/v2/data/search-index.json` and `/files/v2/en-US/data/search-index.json`, retaining `n`/`cn` and adding optional `en`
- Published-only lyrics index/detail files under `/files/translation/lyrics/` and each locale's `/files/v2/{locale}/translation/lyrics/`

Supported locales are exactly `ja-JP`, `zh-CN`, and `en-US`. `ja-JP` is source-only, and `en-US` is stored independently and is never changed by CN sync or AI translation. Chinese search output remains the compact `{id,n,g,c?,cn?}` schema.

Cache and revalidation policy, applied per asset key:

| Asset | `Cache-Control` | Other headers |
| --- | --- | --- |
| Lyrics index and detail | `public, max-age=15, must-revalidate` | strong `ETag`, `Access-Control-Allow-Origin: *` |
| Every other public asset | `public, max-age=300, stale-while-revalidate=3600` | strong `ETag`, `Access-Control-Allow-Origin: *` |

The lyrics pair drops `stale-while-revalidate` on purpose: index and detail are read as one consistent pair and expire on independent timers, so a long TTL would let an edge node answer with a detail that predates the index publication it is validated against. The `ETag` is a strong quoted digest of the exact bytes; `If-None-Match` returns `304`. `GET` and `HEAD` are the only accepted methods, and the permissive CORS header is repeated on `404` and `405` responses so a cross-origin caller reads the status instead of an opaque failure. During drain every public response becomes an observable, logged, CORS-enabled `503`.

Lyrics assets rebuild as one set; a malformed publication preserves the complete previous set rather than exposing a partial index/detail update. The standalone production image embeds the accepted public-only v3 runtime bundle `server/internal/publiclyricsbundle/public-v3.tar.gz` as the reviewed immutable base. It is a self-describing closed inventory with bidirectional 1-to-1 completeness containing only `index.json` and `music_<id>.json`: no manifest, receipt, producer SQLite database, recovery evidence, or private input. Its archive SHA-256 and every count are pinned once in `contracts/public-lyrics/baseline.json`, which `scripts/verify-public-lyrics-baseline.py` checks the committed artifact against; this document deliberately restates neither.

On every files-service projection rebuild the database-backed lyrics projection overlays that bundle: a database publication in state `complete` or `game_only` with a revision greater than the bundle entry, a publication for a music ID absent from the bundle, or any newer non-draft publication replaces or adds that index entry, marks the music ID as database-owned, and replaces its detail bytes. The merged index is re-marshalled with the same deterministic generator marshalling and trailing newline and mirrored to all supported `v2/{locale}/translation/lyrics/` paths. Draft or incomplete database states never override a reviewed `complete` or `game_only` bundle entry, and a failed database projection serves the pure bundle bytes. A bundle that fails to load does not block the rebuild: the projection continues from the database alone and reports `degraded` in its status. An explicitly unpublished song is removed from the merged index and from its detail route even when the bundle contains it; unpublish records that withdrawal in `song_lyrics_public_withdrawals` inside the same transaction that deletes the publication row, publish clears it, and content backups carry the markers. The overlay is a runtime publication overlay only: it never replaces or mutates the production SQLite database and is not copied into Git/S3 content backups.

A successful `POST /api/editor/v1/lyrics/publish` or `POST /api/editor/v1/lyrics/unpublish`, a translation-edition create/clone/rename/set-default mutation, and a `music`/`title` batch each request an immediate rebuild (`PublishNow`), so a publication reaches the public site without waiting for the debounced rebuild. Canonical Public Lyrics v3 JSON Schemas and consumer fixtures for MoeSekai are committed under `contracts/public-lyrics/v3/`; legacy v1 fixtures remain only for backward-compatibility checks.

Raw event scenario snapshots, source notes, license notes, source URL, page/revision/SHA identity, fetch timestamps, editor identity, and draft status are authenticated/private data and never enter legacy or v2 public JSON.

## Console And SekaiText APIs

The optional `locale` on `GET /api/categories`, `GET /api/entries`, `PUT /api/editor/v1/entry`, `GET /api/event-stories`, `GET /api/event-story`, and `PUT /api/editor/v1/event-story/update` accepts only the three supported locales. Omitted locale delegates to the exact legacy Chinese code path; explicit `zh-CN` event detail reads use the localized segment projection and its mutations and audit rows commit atomically without changing omitted-locale behavior. Localized event rows expose IDs and source hashes, and every explicit-locale write must echo and validate the full episode/type/key/ID/hash identity or receive a contract error or conflict.

SekaiText-Moe uses three additive authenticated routes:

- `GET /api/category/snapshot?category={category}&locale={locale}` requires an explicit supported locale and returns `{category, locale, revision, fields}` for every source-backed identity in every category field from one SQLite transaction. `revision` is an opaque URL-safe digest; clients must not construct or interpret it.
- `PUT /api/editor/v1/category/batch` accepts `{category, locale, baseRevision, updates, clientId?}`. It rejects a stale complete-category revision or any unknown/duplicate entry identity before writing, then applies all changed entries and their content-minimized audit rows in one transaction. Success returns the full `{category, locale, revision, fields}` snapshot plus `updated`, the exact number of values that differed from the base snapshot rather than the submitted update count. A complete no-op returns `updated: 0` with the unchanged revision; stale revisions return `revision_conflict` with the current snapshot.
- `GET /api/projection/status` returns the last published `generation`, whether a rebuild is `pending`, `lastSuccessAt`, and a sanitized `lastError`. Database persistence is complete when a write returns; public `/files` and `/translation` bytes for that save are rebuilt only after the post-save status reaches a later non-pending generation with an empty `lastError`. `POST /api/projection/publish` requests one immediate full rebuild and returns the same status object.

`PUT /api/editor/v1/entry` without a `response` selector preserves the exact legacy success body `{status:"ok"}` or `{status:"noop"}`. A client may request exactly one `response=correlated-v1`; any other or duplicate selector returns `400`. The negotiated success body contains exactly `status`, `category`, `field`, `key`, `text`, and `source`, plus `locale` only when the request selected a nonblank explicit locale.

`GET /api/event-story/episode-snapshot?eventId={id}&episodeNo={episode}&locale={locale}` is authenticated and requires an explicit supported locale. One SQLite read transaction returns event/episode/locale identity, an opaque revision covering scenario SHA plus segment identity/source hash/text/source/revision, the localized episode segments, and `scenario` with `{scenarioId,fileName,sha256,parserVersion,rawJson,sourceTalks}`. Parser version 1 follows the public SekaiText Next JSON loader order for TalkData, close-window blanks, effect types 8/18/23 and trailing-blank removal, and exposes `talkDataIndex` so body/speaker segment positions map to `i*2`/`i*2+1`.

Read-only console endpoints and the operational probes answer write methods with `405` and `Allow: GET, HEAD`. Unknown `/api/` paths return the JSON `404` contract instead of falling through to the static console. JSON request bodies are capped at 8 MiB and reject unknown fields, trailing second values, and duplicate object keys at every nesting level. Editor mutations accept only the closed translation source vocabulary `cn`, `human`, `pinned`, `llm`, and `unknown`.

## Single-Instance Editor Gate

The server process owns one writer-preferred editor gate. `GET /api/editor-gate/status` requires JWT authentication, is `Cache-Control: no-store`, and returns exactly version 1 `{version, instanceId, revision, generation, completedGeneration, running, lastRun}`. `instanceId` is a random 32-byte base64url value generated for each process start. Producer start increments `generation` and `revision` and publishes `running=true` before waiting for existing editors; completion, including failed jobs, sets `completedGeneration=generation`, increments `revision`, records an RFC3339 completion time, clears `running`, and releases waiters. Therefore `completedGeneration <= generation`. An `/sse` connection receives the current `gate.status` as its first frame, so a freshly opened tab knows the writable state without polling.

Every content write goes through the strict routes:

- `PUT /api/editor/v1/entry`
- `PUT /api/editor/v1/category/batch`
- `PUT /api/editor/v1/event-story/update`
- `POST /api/editor/v1/event-story/promote-human`
- `PUT /api/editor/v1/lyrics/save`
- `POST /api/editor/v1/lyrics/translation-editions`
- `POST /api/editor/v1/lyrics/publish`
- `POST /api/editor/v1/lyrics/unpublish`
- `POST /api/editor/v1/lyrics/{musicId}/collab-ticket` and `POST /api/editor/v1/lyrics/{musicId}/checkpoint`
- `POST /api/editor/v1/admin/lyrics-source-reviews/import`
- `POST /api/editor/v1/backup/push`

Every strict mutation must send exactly one revision-bound `X-Moe-Loaded-Producer-State: <instanceId>:<revision>:<completedGeneration>` header taken from the status loaded with the edited document. A missing header returns `428`; a duplicate or malformed/base64/non-canonical/out-of-safe-range value returns `400`; an active producer, stale revision, stale completed generation, or process-restart instance mismatch returns `409` with the exact current producer status object. Validation and shared editor acquisition are atomic, and the atomically accepted producer status is carried in request context rather than reacquired inside handlers.

The nine unversioned write routes (`PUT /api/entry`, `PUT /api/category/batch`, `PUT /api/lyrics/save`, `POST /api/lyrics/translation-editions`, `POST /api/lyrics/publish`, `POST /api/lyrics/unpublish`, `PUT /api/event-story/update`, `POST /api/event-story/promote-human`, `POST /api/backup/push`) were deleted and now answer the JSON API `404`. `POST /api/admin/lyrics-source-reviews/import` is the one remaining lenient-gate write route, kept until SekaiText-Moe sends the producer-state header; its strict twin is already registered. Translation sync, all AI/retry/reorder translation operations, and backup restore are producers; duplicate producers fail immediately instead of waiting. The existing `/api/translate/status` response shape remains unchanged for native proxy compatibility.

Verified lyrics imports are accepted only through `/api/editor/v1/lyrics/save`. Source preview is revision-zero/first-save-only, compares exact stopped producer status before and after the external fetch, and rechecks that no lyrics document was created during that fetch before issuing any token. Its grant binds user, music, exact preview, expiry, and the complete atomically accepted producer status; claim marks it in flight, correctable draft validation and 5xx outcomes release the exact claim for retry, and success or deterministic invalidation consumes it. Concurrent use of one token permits only one claimant.

## Lyrics Collaboration

Lyrics draft collaboration uses browser `yjs`/`y-websocket` and `github.com/reearth/ygo` in the existing Go process; no Node.js, V8, or separately deployed collaboration service is part of the runtime contract. The authenticated entry point is exactly `POST /api/editor/v1/lyrics/{musicId}/collab-ticket`, whose closed optional body is absent, `{}`, or `{musicId}` and which returns exactly `{ticket,room,expiresAt}`. A ticket is random, process-local, expires after 45 seconds, is consumed by the first attempted upgrade, and is bound to the authenticated username, role and token generation, music ID, collaboration epoch, and the atomically accepted stopped editor-gate snapshot. The WebSocket endpoint is exactly `/yjs/lyrics/{musicId}?ticket=<one-time-ticket>`; a long-lived JWT must never appear in that URL, and the server rewrites the room to the internal identity `lyrics-{musicId}-e{epoch}`.

Each document has the root map `lyrics` and `schemaVersion: 1` with nested `Y.Map`/`Y.Array`/`Y.Text`; an opaque whole-document JSON string is not conforming. Items in `segments` and `ruby` carry collaboration-only `__yjsId`, `__yjsGeneration`, and optional `__yjsOrigin` fields that materialization strips. Mixed legacy/identified items, incomplete metadata, duplicate IDs, or multiple generations derived from the same origin are a closed structural conflict: the browser stops automatic reconnect and keeps the authoritative REST document read-only, and server checkpoint materialization returns `invalid_collaboration_document`.

`POST /api/editor/v1/lyrics/{musicId}/checkpoint` is the only materialization operation. It revalidates the editor gate and the authoritative base revision/hash and commits the authoritative lyrics mutation, collaboration snapshot/base envelope, and checkpoint ledger in one SQLite transaction. `lyrics_collab_documents.epoch` is a monotonic database fencing generation checked in the same transaction as every persisted update; backup restore fences every room epoch in the restore transaction, and the ledger deliberately has no cascading catalog foreign key so catalog delete/reinsert cannot reset an epoch. SQLite's normalized lyrics and source-v3 tables remain authoritative for API reads, content backup, restore, audit, and public projection.

Ygo limits are mandatory nonzero code-owned production defaults: 50 global connections, 10 peers per room, 256 rooms, 128 resident rooms, an 8 MiB raw update and merged-document cap, an 8 MiB + 64 KiB WebSocket message cap for Yjs framing overhead, 100,000 pending CRDT items, 20 messages/second with burst 40, a 256-message peer write queue, 256 KiB and 256 clients of awareness per room, a 10-second handshake, 90-second awareness expiry, five-minute idle-room eviction, and a one-second maximum persistence-coalescing wait, compacting after every 100 successful flushes. They are not environment-configurable in this release.

## Lyrics Sources And Private Review

An ordinary first save may omit `sourceUrl` or store a valid non-managed external reference. A URL on the exact managed Vocaloid Wiki origin is rejected on an ordinary first save; complete page/revision/SHA1/fetch provenance for that origin is accepted only through the verified preview/import methods. Every provenance-bearing save and restore requires an exact lowercase 40-hex source SHA1. Contract errors use sanitized codes including `revision_conflict` (409), `source_drift`, `segment_mismatch`, `invalid_performer`, and `incomplete_publication` (422). Pinned identity establishes consistency with the fetched revision; it does not establish copyright ownership or permission to publish. Public publication requires non-empty operator-authored `attribution`, which together with private `licenseNote` and `sourceNote` is operator metadata rather than a verified grant.

Phase 1 discovery and Phase 2 fixed-revision fetching are independently disabled by default. `LYRICS_DISCOVERY_ENABLED=true` seeds `lyrics_discovery.enabled` and `LYRICS_FETCH_REVISION_ENABLED=true` seeds `lyrics_discovery.fetch_revision.enabled`; after the first seed, authenticated settings are authoritative. Only one explicit full target with complete role-bound credits is scanned automatically; game-size siblings are association evidence only, and missing/contradictory version metadata or short/preview/partial/cover/medley signals fail closed into private review. The separately gated fetch worker performs an uncached MediaWiki request by exact revision ID and rejects cross-page, revision, SHA1, title, URL, category, origin, restriction, version, markup, response-size, raw-byte, or extraction drift. Both workers are constructed before but start only after successful TCP bind; shutdown drains admission, cancels active work, waits for both loops, and only then closes SQLite. Lease, job-timeout, idle, retry, and discovery scan timings are bounded environment-configurable milliseconds; invalid ranges fail startup.

The canonical private review endpoints are exactly `GET /api/admin/lyrics-source-reviews`, `GET /api/admin/lyrics-source-reviews/detail?reviewId=`, `PUT /api/admin/lyrics-source-reviews/decision`, `PUT /api/admin/lyrics-source-reviews/candidate-selection`, and `POST /api/admin/lyrics-source-reviews/import`. Every route uses bearer-header `RequireAdmin`, `no-store`, bounded closed DTOs, and expected-version CAS; PUT and POST require `application/json`. Batch success is exactly `{items,replayed}` with every item exactly `{reviewId,state,version}`. Actor-scoped idempotency keys are shared across single/candidate decision rows and batch parent rows: only the same request kind and exact payload replays, while cross-kind/payload reuse or any derived batch-child collision returns deterministic `idempotency_conflict` before mutation. Raw wikitext and internal artifact/analysis/extracted-line hashes never enter these APIs, lists, logs, content SSE, public files, or shared Git/S3 content backup.

The import route's closed request is `{reviewId}`. It revalidates approved review/gate state, pinned policy versions, the complete current catalog target grouping and fingerprints, immutable source identity, structured extraction digest, ruby/segment invariants, and performer projection in the first-save transaction, then creates revision 1 as a private editable draft with empty `zh-CN`/`en-US` translations and does not publish it. Exact replay is idempotent with `changed:false`; a nonidentical existing document returns `lyrics_already_saved`.

Sekaipedia's music-ID-to-page-title bindings and song-scoped contributor aliases are database configuration, not compiled constants: administrators edit them under 管理设置 → 歌词来源映射（Sekaipedia） through `GET /api/admin/lyrics-providers/sekaipedia/targets` and `PUT`/`DELETE /api/admin/lyrics-providers/sekaipedia/targets/{musicId}`. A mutation is stored only after the provider registry accepts the whole would-be map, and the running server then installs the new registry without a restart. The fixed `List of songs` index revision pin stays compiled into the binary.

## Database Migrations

Migrations are applied in version order inside individual SQLite transactions. Each applied row records its version, name, SHA-256 checksum, and timestamp in `schema_migrations`; startup rejects changed or newer migration histories. The current schema version is 36.

1. `multilingual_content_and_lyrics` adds locale side tables, stable event segments, catalog tables, lyrics drafts, line segments, and publication snapshots, backfilling only source text the legacy schema actually retained.
2. `lyrics_source_provenance_and_stanzas` adds immutable source revision identity and stanza boundaries.
3. `lyrics_catalog_source_identity` adds catalog producer metadata used to reject ambiguous external source matches.
4. `rolling_event_side_tables_no_legacy_cascade` removes cascades from legacy story parents so a previous binary's replace-import cannot erase multilingual content.
5. `stable_event_title_segment_identity` upgrades migrated title IDs to the positional `:title:-1` identity used by current imports without losing existing localizations.
6. `mark_legacy_event_talk_identity` retains migrated talk positions as opaque `:legacy` IDs because filtered legacy output cannot truthfully identify `body` versus `speaker`.
7. `public_lyrics_attribution_and_token_generation` adds operator-authored public lyrics attribution and per-user token generations, clearing existing publication snapshots because private notes cannot substitute for public attribution.
8. `event_story_scenario_snapshots` adds a no-parent-FK side table keyed by event/episode for deterministic compact JP Unity scenario JSON and SHA-256.
9. `retain_rolling_event_segment_recovery_rows` removes the event/episode/kind/position uniqueness constraint from stable segment recovery rows so rolling imports preserve displaced localization candidates.
10. `durable_lyrics_discovery_jobs` adds the fenced at-least-once queue used by automatic lyrics-source discovery.
11. `lyrics_discovery_shadow_results` extends the queue with catalog fingerprint and policy generation and adds the private Shadow result table.
12. `enforce_lyrics_discovery_integer_types` adds append-only insert/update guards for all numeric queue and Shadow-result fields.
13. `private_lyrics_source_artifacts` adds catalog evidence columns, exact expected fetch SHA1, and immutable bounded raw-source Artifacts.
14. `versioned_lyrics_source_analysis_outputs` adds immutable analysis, association, and job-output records.
15. `private_lyrics_source_review_queue` adds private candidate/artifact reviews and append-only decisions.
16. `overall_lyrics_source_artifact_review_decisions` adds the atomic overall artifact decision while preserving legacy decisions.
17. `lyrics_source_review_batch_idempotency` adds the strict immutable batch parent ledger.
18. `structured_lyrics_source_analysis_evidence` pins selected-version, performer, and ruby-generator evidence for structured extraction.
19. `editable_song_lyrics_ruby` adds persisted editable ruby spans, deterministically removes legacy empty no-op segments, repairs the lowest-position empty segment from non-empty parent Japanese text when a line otherwise has only empty segments, backfills exact-text ruby, and enforces that every persisted segment has non-empty ruby spans concatenating exactly to the segment.
20. `versioned_lyrics_discovery_fixed_candidate_identity` adds the closed versioned complete candidate identity to fixed-revision queue targets and makes every target identity field immutable.
21. `provider_scoped_lyrics_source_provenance` binds durable lyrics-source evidence to an explicit provider and rejects unverifiable legacy origins.
22. `lyrics_source_game_projection_and_ruby_contract` adds source-fetched RFC3339 identity, game projection fields, and persisted ruby/segment contract guards.
23. `sekaipedia_lyrics_source_provenance` extends the closed provenance model to the Sekaipedia provider without rewriting stored source bytes.
24. `additive_lyrics_recovery_import_storage` adds recovery-import batches/items and their immutable runtime ownership checks.
25. `lyrics_source_document_schema_v2` adds the v2 source-document schema and fixed-revision extraction contract.
26. `lyrics_translation_and_proofreading_credits` adds independent translation and proofreading credits.
27. `lyrics_peer_renditions_and_localizations` adds peer renditions and locale-specific rendition text/localization storage.
28. `embedded_lyrics_editor_seed_ledger` adds an immutable private ledger for the production image's canonical editor seed and explicit text-free availability ownership. The ledger never stores raw provider payloads or recovery evidence.
29. `lyrics_translation_versions` adds the peer-side Full/Game translation line table while keeping the v27 primary-side representation byte-compatible; historical rows continue to mean Full when present and otherwise Game.
30. `lyrics_translation_editions` adds document-level translation edition identities and default-edition state; existing v27/v29 rows remain the implicit main edition until the first metadata mutation materializes the schema.
31. `lyrics_yjs_collaboration` adds the epoch-fenced collaboration document snapshot, append-only checksummed update log, and append-only checkpoint ledger. The document epoch is monotonic and deliberately has no cascading catalog foreign key, so restore, canonical replacement, or catalog delete/reinsert cannot make a retired room writable again.
32. `song_682_translation_editions` promotes song 682 to a source-v3 document with multi-edition translations, and its seed runs only when no source document already owns that music ID or document digest.
33. `song_682_translation_qed_correction` corrects one translated line of song 682 in both the edition and rendition tables and advances its edition state revision.
34. `song_682_translation_mirror_sync` synchronizes the legacy rendition localization mirror revision with the authoritative edition state for song 682, leaving mirror rows without edition state untouched.
35. `song_lyrics_public_withdrawals` adds the explicit withdrawal table the public projection applies last, because deleting a publication row cannot remove a song the embedded reviewed bundle also contains.
36. `lyrics_provider_page_targets` moves the reviewed Sekaipedia song map out of the binary: `lyrics_provider_page_targets` holds the music-ID-to-page-title bindings and `lyrics_provider_contributor_aliases` the song-scoped contributor aliases, seeded with exactly the 37 targets and 26 aliases earlier releases compiled in.

The song-682 migrations v32-v34 were reissued while rolling out, so `historicalMigrationChecksums` accepts exactly their recorded digests in addition to the current SQL checksum; no other migration may drift. Migrations after v34 must be pure DDL: a test refuses any later migration that carries a Go hook or that writes the lyrics/catalog content tables.

Before the first pending migration in one startup, file-backed databases receive a verified `*.pre-migration-vN.bak` SQLite backup, where `N` is that first pending version. A multi-version jump therefore produces one recovery point for the pre-upgrade database, not one backup per intermediate migration. Startup also requires the recorded migration history to be a contiguous prefix with matching names/checksums and runs a full `PRAGMA integrity_check` after schema/migrations before returning the database to the server. Migration tests cover idempotent reopen, checksum/gap refusal, injected rollback, backup recovery, legacy writer compatibility, private file modes, old event replacement, explicitly pinned v10-v30 checksums, private-source schema rollback, and the deterministic v19 empty-segment repair plus exact ruby invariant.

Migration v9 requires a single-instance `Recreate` rollout. Before starting the v9 binary, stop the old instance and create a verified full SQLite off-host backup. Do not run old and new writers concurrently and do not roll back an old binary onto a v9 database. When upgrading across v8 and v9 together, restore the verified backup named for the first pending version (for example `*.pre-migration-v8.bak`) or the off-host snapshot as described in `ROLLBACK_RUNBOOK.md`.

## Offline Module Boundary

Every offline operator command and its private packages compile from the nested Go module `server/offline` (`moesekai/server/offline`, which replaces `moesekai/server` with `../`). The production module never requires that module, and `server/production_deps_test.go` asserts that `go list -deps .` for the server binary contains no `moesekai/server/offline/` package. CI runs `go test` and `go vet` separately in `server/` and `server/offline/`. The main module's `cmd/` contains only `migrate`.

`lyrics-stage` encodes catalog contract version 18 in reports/manifests, accepts immutable standalone runtime schema v18, v19, and v20 snapshots only, requires the v18 catalog columns and `catalog-identity-v2` fingerprints, and rejects future runtime schema versions until compatibility is reviewed. `lyrics-import-stage` is never copied into the production image or invoked by the server: it requires absolute manifest/database/backup/receipt paths, the verified backup SHA-256, an audit operator, and `-confirm-local-offline`; it refuses `MOESEKAI_PRODUCTION`, acquires the same single-instance database ownership lock, pins input and database inodes, rejects SQLite sidecars, and reserves the private receipt with `O_EXCL`. Import revalidates the manifest's closed schema/digests, complete current catalog generation, policy/fingerprints/targets/associations, fixed page/revision/SHA1 URL identity, performer mapping, empty translations, and exact ruby/segment structure. Projection accepts only IDs in the runtime's closed game-character performer catalog; when catalog evidence contains only `outside_character` vocals the private draft stores a concrete empty `performerIds` array rather than fabricating a colliding ID, and ordinary publication validation continues to block it. All new drafts and audit rows commit in one transaction; exact existing documents replay, any nonidentical document conflicts, and any item failure rolls back the complete batch. Schema-v2 staged manifests carry each item's actual fixed-revision `source.fetchedAt`, which import writes as `sourceFetchedAt`.

## Backup And Restore

Git and S3 backups retain the legacy category/event `translations` restore projection, physically archive the SQLite-snapshot public lyrics projection as `translations/lyrics/index.json` and `translations/lyrics/music_<id>.json`, and add `translation-content/manifest.json`. The archived public lyrics bytes must exactly equal the corresponding `PublishedLyricsJSON` bytes from the same SQLite snapshot. Both backup projections are materialized from one SQLite snapshot; manifest schema version 1 checksums and counts multilingual entries, stable event content, catalog/lyrics drafts, source provenance, and publication snapshots. Drafts, private provenance, and publication database state remain preserved by `translation-content/lyrics.json` so restore can reconstruct the editable SQLite state. Legacy and additive restore data commit in one transaction, failure rolls everything back, and backups without the additive directory explicitly clear multilingual/lyrics-only state. If the target already contains native Public Lyrics source-v3 documents, application-level content restore replaces them atomically, suspending the source-document delete guards inside the restore transaction and reinstating them before commit. Shared restore preserves all private source rows and supersedes only stale pending review fingerprints. V2 locale projections and search indexes are not archived, and backup push is content backup only — not deployment, static publication, or CDN synchronization. `BackupAll` fails, does not advance `LastBackup`, and does not consume scheduler success when both targets are disabled.

Schema-version-1 `translation-content/event-stories.json` additionally contains canonical scenarios; its legacy `count` remains segments + localizations + locale metadata while optional `scenarioCount` validates the new rows. Restore safety limits keep ordinary files at 64 MiB while allowing only `translation-content/event-stories.json` up to 512 MiB; expanded archives remain bounded at 1 GiB, compressed S3 responses at 256 MiB, and additive content at 1,000,000 aggregate typed records.

The content backup deliberately excludes: user tables, password hashes, settings, token generations, audit records, secrets, raw provider payloads, the embedded release bundles, and the two v36 provider-target tables (`lyrics_provider_page_targets` and `lyrics_provider_contributor_aliases`), which are operator configuration rather than translated content. Restoring a backup therefore never rewrites the Sekaipedia map; it is re-seeded by migration and edited through the admin API. Consequently this content backup is not a full database backup: production operations must additionally create full SQLite snapshots with SQLite's online backup API, `.backup`, or `VACUUM INTO`, verify `PRAGMA integrity_check`, encrypt the snapshot, and transfer it to independently controlled off-host storage. Copying only the main `.db` file while WAL writes are active is not a valid backup. Full snapshots must be taken before migration v9 and before rollback-sensitive releases.

## Standalone Image Invariants

Production mode is explicitly enabled with `MOESEKAI_PRODUCTION=true`. The standalone production image both persists that value and replaces the development server with a binary link-stamped as `next-production`, so a deployment-level empty/false/case/whitespace override is rejected instead of disabling production checks. The image also persists `WORKSPACE_MODE=disabled`, the immutable bundled console root `WEB_DIR=/app/web`, `DB_PATH=/data/moesekai.db`, `DATA_DIR=/data`, and exact `TZ=UTC`. `WORKSPACE_WEB_DIR` and `WORKSPACE_MANIFEST_SHA256` must be unset; any missing or non-exact production value fails during `--verify-runtime` before the persistent data path is touched, and the container entrypoint runs that preflight before database ownership/open, upstream validation, or worker construction. Production startup then sets `time.Local = time.UTC`. Literal, decoded, and normalized paths entering the retired `/workspace` return `404 no-store` before preflight and ServeMux, with no console fallback. Runtime identity is `65532:65532` with a read-only root, a writable persistent `/data`, and a bounded `/tmp` tmpfs; one process owns the SQLite location for its lifetime.

Production also requires at least 32 bytes of `MOESEKAI_MASTER_KEY` secret material and at least one initialized admin; a fresh database must receive a valid `ADMIN_PASSWORD` or `TRANSLATOR_ACCOUNTS` bootstrap secret. `editor` and `admin` are the complete role vocabulary. Settings patches reject unknown keys before commit, and `backup.daily_hour` accepts only canonical integer strings from `0` through `23`. Publication uses a directory-durable incomplete marker; an unconfirmed post-rename target is removed or rejected by the entrypoint instead of being accepted on restart.

The same binary embeds one private canonical editor seed at `server/internal/embeddedlyricsseed/editor-seed.tar.gz`, whose archive SHA-256 is pinned in `contracts/public-lyrics/baseline.json`. Immediately after SQLite opens and before environment settings or bootstrap accounts may write, startup inspects the live catalog: an empty catalog is explicitly deferred so the existing first-boot bootstrap can initialize it, while every nonempty catalog must match the canonical music IDs, Japanese titles, `catalog-identity-v2` fingerprints, and aggregate digests exactly. One exclusive SQLite transaction then fills only music IDs with no existing legacy draft, source document, recovery availability document, or previously inserted embedded availability ownership; existing ownership is recorded as `preserved_existing` and never overwritten. The batch and item ledger is immutable, restart replay validates the exact batch and reports zero new changes, and any catalog mismatch rolls back without a seed batch or item. The archive contains no raw recovery evidence, provider payload, producer database, credentials, users, settings, ordinary translations, stories, reviews, or publications, and is never served by `/files` or `/translation`.

`/readyz` requires SQLite, at least one successfully published initial public projection with no known latest-generation failure, and a live or validated cached search index; `/healthz` remains independent liveness. Initial generation runs asynchronously after the listener is acquired, and every failed requested publication retries with bounded exponential backoff until the latest requested generation publishes or shutdown cancels the worker. On drain, only exact `GET`/`HEAD` `/healthz` and `/readyz` remain admitted. One configurable total shutdown budget covers a short HTTP drain, cancellation, forced HTTP close, and all tracked worker/request joins before SQLite closes; if a noncancelable filesystem or SQLite critical section exceeds it, a watchdog logs a critical fail-closed message and exits.

JWTs carry a persisted per-user token generation and are accepted only while the user still exists and the current database role and generation match. Password changes, role changes, and deletion immediately reject previously issued tokens. Public setup and login attempts are bounded in memory by both the normalized account and the socket `RemoteAddr`; forwarding headers are intentionally ignored. Editors may proofread individual entries, event lines, and lyrics drafts; CN sync, every AI trigger, event retry/reorder/promote, backup push/restore, user/settings/upstream administration, provider-target administration, and lyrics publication are admin-only.

Image build, digest pinning, signing, and the manual publication workflow are defined in `STANDALONE_RELEASE.md`; production rollback is defined in `ROLLBACK_RUNBOOK.md`.
