# Locale And Lyrics Production Contract

This document records the additive contract implemented on top of legacy baseline `bbc3340`. The baseline behavior and fixtures in `LEGACY_BASELINE.md` remain authoritative for requests without an explicit locale and for all existing public files.

## Database Migrations

Migrations are applied in version order inside individual SQLite transactions. Each applied row records its version, name, SHA-256 checksum, and timestamp in `schema_migrations`; startup rejects changed or newer migration histories.

1. `multilingual_content_and_lyrics` adds locale side tables, stable event segments, catalog tables, lyrics drafts, line segments, and publication snapshots. It backfills only source text that the legacy schema actually retained.
2. `lyrics_source_provenance_and_stanzas` adds immutable source revision identity and stanza boundaries.
3. `lyrics_catalog_source_identity` adds catalog producer metadata used to reject ambiguous external source matches.
4. `rolling_event_side_tables_no_legacy_cascade` removes cascades from legacy story parents so a previous binary's replace-import cannot erase multilingual content. Current imports explicitly reconcile stable segment rows.
5. `stable_event_title_segment_identity` upgrades migrated title IDs to the same positional `:title:-1` identity used by current imports without losing existing localizations.
6. `mark_legacy_event_talk_identity` retains migrated talk positions as opaque `:legacy` IDs because filtered legacy output cannot truthfully identify `body` versus `speaker`; localization rows and source hashes move with those IDs. A current-format reimport reserves matching stable IDs first, then carries a localization to a different ID only when its source occurrence was unique before reimport and identifies exactly one unclaimed episode/kind/hash destination afterward.
7. `public_lyrics_attribution_and_token_generation` adds operator-authored public lyrics attribution and per-user token generations. Existing lyrics publication snapshots are cleared because private notes cannot be substituted for public attribution; drafts remain intact and require attribution before an administrator republishes them.
8. `event_story_scenario_snapshots` adds a no-parent-FK side table keyed by event/episode for deterministic compact JP Unity scenario JSON and SHA-256. The lack of a legacy parent FK is intentional: an older writer can continue replacing event parents without cascading private scenario snapshots, while current reads validate parent/scenario identity and fail closed.
9. `retain_rolling_event_segment_recovery_rows` removes the event/episode/kind/position uniqueness constraint from stable segment recovery rows. This preserves displaced localization recovery candidates during rolling legacy/current event imports; the primary segment ID and localization foreign key remain authoritative, and current reconciliation still validates source identity before carrying content forward.
10. `durable_lyrics_discovery_jobs` adds the fenced at-least-once queue used by automatic lyrics-source discovery. Job identity, attempts, lease ownership/expiry, retry scheduling, terminal state, and optimistic version are persisted; this migration remains unchanged after application.
11. `lyrics_discovery_shadow_results` append-only extends the queue with catalog fingerprint and policy generation, then adds the private Shadow result table. Composite foreign-key identity prevents a result from being attached to a different catalog or policy generation; outcome/count/JSON constraints fail closed before persistence.
12. `enforce_lyrics_discovery_integer_types` adds append-only insert/update guards for all numeric queue and Shadow-result fields.
13. `private_lyrics_source_artifacts` adds catalog evidence columns, exact expected fetch SHA1, and immutable bounded raw-source Artifacts.
14. `versioned_lyrics_source_analysis_outputs` adds immutable analysis, association, and job-output records.
15. `private_lyrics_source_review_queue` adds private candidate/artifact reviews and append-only decisions.
16. `overall_lyrics_source_artifact_review_decisions` adds the atomic overall artifact decision while preserving legacy decisions.
17. `lyrics_source_review_batch_idempotency` adds the strict immutable batch parent ledger.
18. `structured_lyrics_source_analysis_evidence` pins selected-version, performer, and ruby-generator evidence for structured extraction.
19. `editable_song_lyrics_ruby` adds persisted editable ruby spans. It deterministically removes legacy empty no-op segments, repairs the lowest-position empty segment from non-empty parent Japanese text when a line otherwise has only empty segments, backfills exact-text ruby, and enforces that every persisted segment has non-empty ruby spans whose text concatenates exactly to the segment. The v18 insert shape that omits `ruby_json` is normalized by a compatibility trigger before statement completion.
20. `versioned_lyrics_discovery_fixed_candidate_identity` adds the closed versioned complete candidate identity to fixed-revision queue targets, reconciles legacy jobs from generic discovery/admin/artifact evidence, aborts on conflicting or unreconcilable metadata, and makes every target identity field immutable.
21. `provider_scoped_lyrics_source_provenance` binds durable lyrics-source evidence to an explicit provider and rejects unverifiable legacy origins.
22. `lyrics_source_game_projection_and_ruby_contract` adds source-fetched RFC3339 identity, game projection fields, and persisted ruby/segment contract guards.
23. `sekaipedia_lyrics_source_provenance` extends the closed provenance model to the Sekaipedia provider without rewriting stored source bytes.
24. `additive_lyrics_recovery_import_storage` adds recovery-import batches/items and their immutable runtime ownership checks.
25. `lyrics_source_document_schema_v2` adds the v2 source-document schema and fixed-revision extraction contract.
26. `lyrics_translation_and_proofreading_credits` adds independent translation and proofreading credits.
27. `lyrics_peer_renditions_and_localizations` adds peer renditions and locale-specific rendition text/localization storage.
28. `embedded_lyrics_editor_seed_ledger` adds an immutable private ledger for the production image's canonical 700-song editor seed and explicit text-free availability ownership. The ledger never stores raw provider payloads or recovery evidence.
29. `lyrics_yjs_collaboration` adds the epoch-fenced collaboration document snapshot, append-only checksummed update log, and append-only checkpoint ledger. `lyrics_collab_documents` stores one schema-v1 Yjs snapshot and authoritative base revision/hash per music ID; `lyrics_collab_updates` appends ordered, checksummed V1 updates keyed by music ID, epoch, and sequence until compaction; `lyrics_collab_checkpoints` records each materialization boundary, actor, old/new authority hashes and revisions, and whether canonical content changed. The document epoch is monotonic and deliberately has no cascading catalog foreign key, so restore, canonical replacement, or catalog delete/reinsert cannot make a retired room writable again.

Before the first pending migration in one startup, file-backed databases receive a verified `*.pre-migration-vN.bak` SQLite backup, where `N` is that first pending version. A multi-version jump therefore produces one recovery point for the pre-upgrade database, not one backup per intermediate migration. Startup also requires the recorded migration history to be a contiguous prefix with matching names/checksums and runs a full `PRAGMA integrity_check` after schema/migrations before returning the database to the server. Migration tests cover idempotent reopen, checksum/gap refusal, injected rollback, backup recovery, legacy writer compatibility, private file modes, old event replacement, explicitly pinned v10-v29 checksums, private-source schema rollback, and the deterministic v19 empty-segment repair plus exact ruby invariant.

The SekaiText category snapshot/batch and projection-status contracts require no additional schema: category revisions are derived from point-in-time content, and event optimistic concurrency uses the existing localization revision columns.

Migration v9 requires a single-instance `Recreate` rollout. Before starting the v9 binary, stop the old instance and create a verified full SQLite off-host backup with SQLite backup/VACUUM semantics. Do not run old and new writers concurrently and do not roll back an old binary onto a v9 database. A `*.pre-migration-v9.bak` exists only when v9 is the first pending migration for that startup; when upgrading across v8 and v9 together, restore the verified backup named for the first pending version (for example `*.pre-migration-v8.bak`) or the off-host snapshot as described in `ROLLBACK_RUNBOOK.md`.

## Console APIs

The optional `locale` on `GET /api/categories`, `GET /api/entries`, `PUT /api/entry`, `GET /api/event-stories`, `GET /api/event-story`, and `PUT /api/event-story/update` accepts only `ja-JP`, `zh-CN`, and `en-US`. Omitted locale delegates to the exact legacy Chinese code path; explicit `zh-CN` event detail reads use the localized segment projection and its mutations and audit rows commit atomically without changing omitted-locale behavior; `ja-JP` is source-only and rejects writes; `en-US` is stored independently and is never changed by CN sync or AI translation. Localized event rows expose IDs and source hashes, and every explicit-locale write, including `zh-CN`, must echo and validate the full episode/type/key/ID/hash identity or receive a contract error or conflict.

SekaiText-Moe can use three additive authenticated routes without changing the legacy per-field routes:

- `GET /api/category/snapshot?category={category}&locale={locale}` requires an explicit supported locale and returns `{category, locale, revision, fields}` for every source-backed identity in every category field from one SQLite transaction. `revision` is an opaque URL-safe digest over source identities, IDs, and locale values; clients must not construct or interpret it.
- `PUT /api/category/batch` accepts `{category, locale, baseRevision, updates, clientId?}`. It rejects a stale complete-category revision or any unknown/duplicate entry identity before writing, then applies all changed entries and their content-minimized audit rows in one transaction. One post-commit change notification schedules public generation, and one existing `entry.updated` or `entry.locale.updated` SSE frame is emitted per changed entry after commit. Success returns the full `{category, locale, revision, fields}` snapshot plus `updated`, where `updated` is the exact number of values that differed from the base snapshot rather than the submitted update count. A complete no-op therefore returns `updated: 0` with the unchanged revision; a partially unchanged batch may return fewer changes than submitted and advances the revision exactly when at least one value changed. Stale revisions return `revision_conflict` with the current snapshot.
- `GET /api/projection/status` returns the last published `generation`, whether a rebuild is `pending`, `lastSuccessAt`, and a sanitized `lastError`. Initial generation runs asynchronously after the listener is acquired, so liveness and signal handling are available while readiness remains false. `/readyz` remains false for every pending generation, even before an error is known, preventing restore or write traffic from being admitted while authenticated SQLite state and public files are temporarily different. Every failed requested publication, including a failure after an earlier success, retries with bounded exponential backoff until the latest requested generation publishes or shutdown cancels the worker. Database persistence is complete when the batch returns; public `/files` and `/translation` bytes for that save are rebuilt only after the post-save status reaches a later non-pending generation with an empty `lastError`.

### Single-Instance Editor Gate

The server process owns one writer-preferred editor gate. `GET /api/editor-gate/status` requires JWT authentication, is `Cache-Control: no-store`, and returns exactly version 1 `{version, instanceId, revision, generation, completedGeneration, running, lastRun}`. `instanceId` is a random 32-byte base64url value generated for each process start. All counters remain within JavaScript's safe integer range. Initially all counters are zero, `running` is false, and `lastRun` is an empty string. Producer start increments `generation` and `revision` and publishes `running=true` before waiting for existing editors; completion, including failed jobs, sets `completedGeneration=generation`, increments `revision`, records an RFC3339 completion time, clears `running`, and releases waiters. Therefore `completedGeneration <= generation`, and while running the generation is exactly one ahead of the completed generation.

Producer-aware clients use these strict aliases:

- `PUT /api/editor/v1/entry`
- `PUT /api/editor/v1/category/batch`
- `PUT /api/editor/v1/event-story/update`
- `POST /api/editor/v1/event-story/promote-human`
- `PUT /api/editor/v1/lyrics/save`
- `POST /api/editor/v1/lyrics/publish`
- `POST /api/editor/v1/lyrics/unpublish`
- `POST /api/editor/v1/backup/push`

Every strict mutation must send exactly one revision-bound `X-Moe-Loaded-Producer-State: <instanceId>:<revision>:<completedGeneration>` header from the status loaded with the edited document. The seven-key status response remains version 1, while the workspace source and editor-gate proof contracts are version 2. A missing header returns `428`; a duplicate or malformed/base64/non-canonical/out-of-safe-range value returns `400`; an active producer, stale revision, stale completed generation, or process-restart instance mismatch returns `409` with the exact current producer status object. Validation and shared editor acquisition are atomic, and the atomically accepted producer status is carried in request context rather than reacquired inside handlers. Existing canonical mutation paths require no new header and remain compatible, but immediately return `409` while a producer is running rather than waiting to apply a stale payload afterward. A lyrics save carrying `sourceImportToken` is the exception: the canonical `/api/lyrics/save` route fails closed with `428`, and verified imports are accepted only through `/api/editor/v1/lyrics/save`. Source preview is revision-zero/first-save-only, compares exact stopped producer status before and after the external fetch, and rechecks that no lyrics document was created during that fetch before issuing any token. Its grant binds user, music, exact preview, expiry, and the complete atomically accepted producer status; claim marks it in flight. Correctable draft validation, database/transaction/internal failure, and 5xx outcomes release the exact claim for retry. Success and deterministic invalidation—expiry, user/music mismatch, producer drift, source/preview drift, nonzero revision, or an already-existing first-save target—commit/consume the exact claim. After claim, `SaveImportedLyricsMutation` retains the fixed per-music stripe across eligibility checks and the complete SQLite transaction; terminal classification occurs only after it returns, and the Store has no grant callback or burn-on-attempt hook. An impossible exact-claim commit failure after a durable save is logged as an internal invariant, the token is invalidated fail-closed, and the API preserves the truthful successful save response rather than reporting a false retryable failure. Concurrent use of one token permits only one claimant. Translation sync, all AI/retry/reorder translation operations, and backup restore are producers. Duplicate producers fail immediately instead of waiting. The existing `/api/translate/status` response shape remains unchanged for native proxy compatibility.

## Lyrics Collaboration

Lyrics draft collaboration uses browser `yjs`/`y-websocket` and `github.com/reearth/ygo` in the existing Go process. No Node.js, V8, or separately deployed collaboration service is part of the runtime contract. The legacy notification/editor-gate channel remains a separate control plane and does not own lyrics document state.

The authenticated entry point is exactly `POST /api/editor/v1/lyrics/{musicId}/collab-ticket`. Its closed optional body is absent, `{}`, or `{musicId}` with the exact same positive integer as the path, and it returns exactly `{ticket,room,expiresAt}`. It is a strict editor operation: the tab must send the exact loaded producer-state proof before it can obtain read-write collaboration authority. The caller's long-lived bearer JWT is accepted only in the HTTP `Authorization` header. A ticket is random, process-local, expires after 45 seconds, is consumed by the first attempted upgrade whether that attempt succeeds or fails, and is bound to the authenticated username, role and token generation, the exact music ID, the current collaboration epoch, and the atomically accepted stopped editor-gate snapshot. Reuse, expiry, user/token drift, path mismatch, producer drift, or epoch drift fails closed before the Yjs document is disclosed. An accepted Yjs connection itself holds editor-gate shared admission until disconnect; a producer first publishes its running generation, causes those rooms to close, and waits for their admissions to release before authoritative replacement proceeds.

The WebSocket endpoint is exactly `/yjs/lyrics/{musicId}?ticket=<one-time-ticket>`. Its query is closed to the short ticket credential; a long-lived JWT, bearer token, access token, or authorization value must never be placed in a Yjs WebSocket URL. The URL `musicId` is checked against the ticket but is never trusted as the internal room name. After authorization the handler rewrites ygo's path value to the canonical internal identity `lyrics-{musicId}-e{epoch}`. The response `room` field is opaque diagnostic identity, not client authority. Each disconnect destroys the provider and obtains a new ticket before reconnecting; old tickets and old-epoch offline documents are never reused.

The Next.js development server proxies `/api/*`, `/sse`, `/ws`, and `/yjs/*` to `BACKEND_ORIGIN` so both WebSocket control planes keep the same browser origin in local development. Production serves the exported console and all of those endpoints from the single Go process.

Each document has the root map `lyrics` and `schemaVersion: 1`. Structured objects and ordered collections are nested `Y.Map` and `Y.Array` values, while editable text is represented by nested `Y.Text`; an opaque whole-document JSON string is not a conforming representation. Awareness is ephemeral presence metadata and is not checkpointed, audited, backed up, or treated as authorization. A client is editable only after the provider emits `sync(true)`. `y-websocket` 3.x has a roughly 30-second no-server-message reconnect watchdog, so the browser sets `resyncInterval` to exactly 15 seconds. This forces a periodic SyncStep1/SyncStep2 exchange and keeps a healthy single-editor room from reconnecting merely because no peer produced traffic.

Items in `segments` and `ruby` carry collaboration-only `__yjsId`, `__yjsGeneration`, and optional `__yjsOrigin` fields. Materialization strips these fields before constructing a canonical lyrics DTO. A structured array with no metadata remains readable as a legacy room, and a conforming client upgrades it on its next structural synchronization. Mixed legacy/identified items, incomplete metadata, duplicate IDs, or multiple generations derived from the same origin are a closed structural conflict: browser materialization returns no document, stops automatic reconnect, and leaves the authoritative REST document read-only; server checkpoint materialization returns `invalid_collaboration_document`. The system does not guess a semantic merge for concurrent segment or ruby splits.

Ordinary Yjs synchronization acknowledges CRDT exchange, not durable canonical save. `POST /api/editor/v1/lyrics/{musicId}/checkpoint` is the only collaboration materialization operation. It is an authenticated strict editor mutation, revalidates the editor gate and the authoritative base revision/hash, decodes the closed schema, and sends the result through the existing lyrics validation, immutable-source, revision, audit, and publication boundaries. The authoritative lyrics mutation, collaboration snapshot/base envelope, and checkpoint ledger commit in one SQLite transaction; any hook or ledger failure rolls all of them back. A first save freezes and drains the revision-zero room before materialization and atomically reseeds the next epoch. Later saves encode authority-owned scalars on a detached document inside the transaction, then update the live room only after commit; a failed live update closes that room so the next connection reloads the durable checkpoint. A no-op checkpoint does not invent a revision. SQLite's normalized lyrics and source-v3 tables remain authoritative for API reads, content backup, restore, audit, and public projection; the persisted Yjs state is a fenced draft/cache and never replaces those contracts.

`lyrics_collab_documents.epoch` is a monotonic database fencing generation, not a connection-local counter. Every persisted update checks the room epoch in the same SQLite transaction and writes with a matching-epoch predicate. Collaboration checkpoints advance their saved envelope or first-save epoch in the authoritative mutation transaction. Backup restore fences every existing room epoch in the restore transaction; only after a successful restore commit does `backup.Manager` close in-memory rooms, clear tickets, and reseed snapshots. An ordinary non-collaboration lyrics mutation immediately reseeds after its successful canonical commit; a crash or reset failure cannot checkpoint the stale room because the authoritative hash/revision check fails, and the next ticket issuance repairs the drift before admitting a peer. The collaboration ledger deliberately has no cascading catalog foreign key, so deleting and reinserting catalog rows cannot reset an epoch to 1. A failed restore rolls back both content and epoch changes and does not run the retirement hook.

Ygo limits are mandatory nonzero code-owned production defaults: 50 global connections, 10 peers per room, 256 rooms, 128 resident rooms, an 8 MiB raw update and merged-document cap, an 8 MiB + 64 KiB WebSocket message cap for Yjs framing overhead, 100,000 pending CRDT items, 20 messages/second with burst 40, a 256-message peer write queue, 256 KiB and 256 clients of awareness per room, a 10-second handshake, 90-second awareness expiry, five-minute idle-room eviction, and a one-second maximum persistence-coalescing wait. Persistence compacts after every 100 successful flushes. These limits are not environment-configurable in this release. Increasing them requires code review, load tests, and an updated production contract.

Entry-save response correlation is additive and explicitly negotiated. `PUT /api/entry` and `PUT /api/editor/v1/entry` without a `response` selector preserve the exact legacy success body `{status:"ok"}` or `{status:"noop"}`. A client may request exactly one `response=correlated-v1`; any other or duplicate selector returns `400`. The negotiated success body contains exactly `status`, `category`, `field`, `key`, `text`, and `source`, plus `locale` only when the request selected a nonblank explicit locale. Omitted or blank request locale therefore remains distinguishable from explicit `zh-CN`. Clients must compare every echoed field before clearing local recovery state. SekaiText-Moe may accept an exact status-only body as an unverifiable fallback during an independent rollout, but it must not treat that fallback as correlated.

Explicit-locale event detail segments also expose their translation `revision`. `PUT /api/event-story/update` conditionally rejects a competing localized translation with `revision_conflict` when the client echoes `revision`; omission retains the prior authenticated client behavior. Event revisions are removed before public v2 serialization, so no existing public event bytes change.

`GET /api/event-story/episode-snapshot?eventId={id}&episodeNo={episode}&locale={locale}` is authenticated and requires an explicit supported locale. A single SQLite read transaction returns event/episode/locale identity, an opaque revision covering scenario SHA plus segment identity/source hash/text/source/revision, the localized episode segments, and `scenario` with `{scenarioId,fileName,sha256,parserVersion,rawJson,sourceTalks}`. `rawJson` is deterministic compact JSON containing the complete JP `ScenarioId`, `Snippets`, `TalkData`, `SpecialEffectData`, and `AppearCharacters`; SHA, parent identity, scenario identity, and canonical form are revalidated before any raw data is returned. Parser version 1 follows the public SekaiText Next JSON loader order for TalkData, close-window blanks, effect types 8/18/23 and trailing-blank removal, and exposes `talkDataIndex` on TalkData rows so body/speaker segment positions map to `i*2`/`i*2+1`.

Lyrics and catalog routes are authenticated:

- `GET /api/catalog/music`
- `GET /api/catalog/characters`
- `GET /api/lyrics` and `GET /api/lyrics/detail`
- `PUT /api/lyrics/save` for editors and admins
- `POST /api/lyrics/publish` and `POST /api/lyrics/unpublish` for admins
- `GET /api/lyrics/source/search` and `POST /api/lyrics/source/preview` for admins

The `next-production` binary also embeds one private canonical 700-song editor seed (archive SHA-256 `a8a2a7c841d0d73e448fd69f9adb236965b3b01a89d2ba58dcc921925e6ea479`). Immediately after SQLite opens and before environment settings or bootstrap accounts may write, startup inspects the live catalog: an empty catalog is explicitly deferred so the existing first-boot translation bootstrap can initialize it, while every nonempty catalog must match all 700 music IDs, Japanese titles, `catalog-identity-v2` fingerprints, and aggregate digests exactly. One exclusive SQLite transaction then fills only music IDs with no existing legacy draft, source document, recovery availability document, or previously inserted embedded availability ownership. It writes 652 source-v3 documents into the native plural rendition tables, one legacy editable document, and 47 explicit text-free availability ledger rows; existing ownership is recorded as `preserved_existing` and is never overwritten. The batch and item ledger is immutable, restart replay validates the exact batch, ledger, and inserted ownership and reports zero new changes, and any catalog mismatch—including a 707-song catalog—rolls back without a seed batch or item. The archive contains no raw recovery evidence, provider payload, producer database, credentials, users, settings, ordinary translations, stories, reviews, or publications. This seed is private image content and is never served by `/files` or `/translation`; the separate Public Lyrics overlay remains read-only public release content.

Lyrics use numeric `musicId`, stable ordered line IDs, Japanese/Chinese/English text, ordered text segments, required unique catalog performer IDs for publication, optimistic revisions, immutable Japanese source hashes and source provenance, draft/publication separation, and idempotent save/publish/unpublish behavior. An ordinary first save may omit `sourceUrl` or store a valid non-managed external reference. A URL on the exact managed Vocaloid Wiki origin, whether or not it includes `oldid`, is rejected on an ordinary first save; complete page/revision/SHA1/fetch provenance for that origin is accepted only through the verified preview/import methods. Other Fandom or Wiki origins are not classified as managed merely by platform or naming similarity. Existing legacy drafts that contain only a managed-Wiki URL remain editable only while the source URL, provenance fields, ordered line IDs/order values, and Japanese source text remain unchanged. Every provenance-bearing save and restore requires an exact lowercase 40-hex source SHA1; short, uppercase, non-hex, or opaque values fail closed. Source lookup pins page and revision identity, rejects cross-origin redirects and explicit no-reprint markers/categories, and records source access in the audit log; contract errors use sanitized codes including `revision_conflict` (409), `source_drift`, `segment_mismatch`, `invalid_performer`, and `incomplete_publication` (422).

Pinned page/revision/SHA1/fetch identity establishes consistency with the fetched revision; it does not establish copyright ownership, permission to reproduce or translate, license compatibility, or permission to publish. Public lyrics publication requires non-empty operator-authored `attribution`, which is the only public source-context metadata field. `attribution`, private `licenseNote`, and private `sourceNote` are operator metadata rather than verified grants or legal conclusions. Source notes, license notes, source URL, page/revision/SHA identity, fetch timestamps, editor identity, and draft status remain confined to authenticated APIs and backups. Canonical Public Lyrics v3 JSON Schemas and consumer fixtures for MoeSekai are committed under `contracts/public-lyrics/v3/`; legacy v1 fixtures remain only for backward-compatibility checks. NEXT paths and field names remain authoritative and no duplicate compatibility editing endpoints are exposed.

Phase 1 discovery and Phase 2 fixed-revision fetching are independently disabled by default. `LYRICS_DISCOVERY_ENABLED=true` seeds `lyrics_discovery.enabled`, while `LYRICS_FETCH_REVISION_ENABLED=true` seeds `lyrics_discovery.fetch_revision.enabled`; after first seed, authenticated settings are authoritative. Discovery applies versioned lexicographic mandatory gates: only one explicit full target with complete role-bound credits is scanned automatically, game-size siblings are association evidence only, and missing/contradictory version metadata or short/preview/partial/cover/medley signals fail closed into private review. Discovery completion atomically stores its bounded shadow summary and either enqueues one versioned complete candidate identity `(pageId, revisionId, expected lowercase SHA1, page title, canonical oldid URL, sorted categories)` fetch job, creates/reuses a candidate review, or records no candidates before fenced success.

The separately gated fetch worker claims only `fetch_revision`, rechecks the catalog fingerprint, carries the versioned complete reviewed candidate identity (page/revision/SHA1, page title, canonical `oldid` URL, and sorted categories), performs an uncached MediaWiki request by exact revision ID, and compares that complete identity both after fetch and again at transactional completion before applying current restriction metadata. It rejects cross-page, revision, SHA1, title, URL, category, origin, restriction, version, markup, response-size, raw-byte, or extraction drift. One fenced transaction insert-or-verifies the immutable bounded raw-wikitext Artifact, immutable versioned analysis and `full_target`/`game_size_evidence` associations, private artifact review, job output, and job success. Raw wikitext is never returned by the five canonical admin APIs, lists, logs, content SSE, public files, or shared Git/S3 content backup. Both workers are constructed before but start only after successful TCP bind; shutdown drains admission, cancels active work, waits for both loops, and only then closes SQLite. Lease, job-timeout, idle, retry, and discovery scan timings are bounded environment-configurable milliseconds; invalid ranges fail startup.

The canonical private review endpoints are exactly `GET /api/admin/lyrics-source-reviews`, `GET /api/admin/lyrics-source-reviews/detail?reviewId=`, `PUT /api/admin/lyrics-source-reviews/decision`, `PUT /api/admin/lyrics-source-reviews/candidate-selection`, and `POST /api/admin/lyrics-source-reviews/import`. Every route uses bearer-header `RequireAdmin`, `no-store`, bounded closed DTOs, and no producer proof; PUT and POST require `application/json`. The frozen list DTO contains only review identity/state, music/title, catalog fingerprint, reason, three compatibility gate states, version/priority, and timestamps; detail adds either immutable candidate identities or safe page/revision/SHA1/categories/fetch facts, policy/outcome/evidence, extracted lines, associations, and append-only decisions. Single/candidate mutation responses contain only review/gate state, version, and replay status; batch success is exactly `{items,replayed}`, with every compact item exactly `{reviewId,state,version}` and replay represented only by the top-level flag. Raw wikitext and internal artifact/analysis/extracted-line hashes are excluded. New artifact review actions use one `overall` approve/reject decision that atomically sets the stored `identity`, `source_use`, and `parse` compatibility states and completes the review in one version increment; historical per-gate decisions remain readable, and a still-pending legacy partially reviewed item can be completed by the same overall action. Candidate selection either chooses one immutable candidate and atomically enqueues its fixed fetch or explicitly excludes it. Decisions are append-only and expected-version CAS conflicts return 409. Actor-scoped idempotency keys are shared across single/candidate decision rows and batch parent rows on the decision route: only the same request kind and exact payload replays, while cross-kind/payload reuse or any derived batch-child collision returns deterministic `idempotency_conflict` before mutation, preserving zero-application rollback.

`POST /api/admin/lyrics-source-reviews/import` is the registered approved-review consumer. Its closed request is `{reviewId}`. It revalidates approved review/gate state, pinned policy versions, the complete current catalog target grouping, current catalog fingerprints, immutable source identity, structured extraction digest, ruby/segment invariants, and performer projection in the first-save transaction. The same closed projection rule used by the offline importer preserves declared human/external labels in source evidence, uses a valid game-character catalog fallback when available, and otherwise stores concrete `[]` for outside-only assignments without fabricating an ID. Success creates revision 1 as a private editable draft with empty `zh-CN`/`en-US` translations and does not publish it; ordinary publication validation continues to block every unassigned segment. Exact replay is idempotent with `changed:false`; a nonidentical existing lyrics document returns `lyrics_already_saved`. Review decisions and candidate selection alone still do not save drafts or change public projections; the explicit import route emits the ordinary private-content change notification only after commit. Shared content restore preserves all private source rows and supersedes only stale pending review fingerprints.

The local staging chain remains separate from production APIs. `lyrics-stage` continues to encode catalog contract version 18 in reports/manifests, accepts immutable standalone runtime schema v18, v19, and v20 snapshots only, explicitly requires the v18 catalog columns and `catalog-identity-v2` fingerprints, and rejects future runtime schema versions until compatibility is reviewed. `lyrics-import-stage` is an offline operator command and is not copied into the production image or invoked by the server. It requires absolute manifest/database/backup/receipt paths, the verified backup SHA-256, an audit operator, and `-confirm-local-offline`; it refuses `MOESEKAI_PRODUCTION`, acquires the same single-instance database ownership lock, pins input and database inodes, rejects SQLite sidecars, and reserves the private receipt with `O_EXCL`. The consumer revalidates the manifest's closed schema/digests, complete current catalog generation, policy/fingerprints/targets/associations, fixed page/revision/SHA1 URL identity, performer mapping, empty translations, and exact ruby/segment structure. Source performer legends remain intact in the immutable manifest. Projection accepts only IDs in the runtime's closed game-character performer catalog: declared human or external source labels are omitted from the numeric projection and use the selected catalog-vocal fallback when one exists. If catalog evidence contains only `outside_character` vocals, the private draft stores a concrete empty `performerIds` array rather than fabricating a colliding game-character ID; ordinary publication validation continues to require at least one valid catalog performer, so those segments remain explicitly editor-reviewable and unpublishable. All new drafts and audit rows commit in one transaction; exact existing documents replay, any nonidentical document conflicts, and any item failure rolls back the complete batch. Schema-v2 staged manifests carry each item's actual fixed-revision `source.fetchedAt`; import writes that exact per-item timestamp as `sourceFetchedAt`, while preflight `generatedAt` remains report-generation metadata only.

JSON request bodies are capped at 8 MiB, reject unknown fields, trailing second values, and duplicate object keys at every nesting level, and the HTTP server bounds both header and whole-request read time. External lyrics-source requests use response caps, rate limiting, cache bounds, a proxy-disabled DNS-pinned public-HTTPS transport, MediaWiki query-string support, exact-origin redirects, and timeouts. HTTP responses carry a sanitized `X-Request-ID`; `/readyz` requires SQLite, at least one successfully published initial public projection with no known latest-generation failure, and a live or validated cached search index. Search masterdata must pass per-source identity, minimum-coverage, and nonreduction checks before replacing the last-known-good assets, and its local translation reads share one restore exclusion boundary. Authenticated `/api/search/status` and admin-protected `/healthz/details` expose the search ready/degraded state and sanitized failure code; health details also report lightweight request/client-error/server-error counters, while `/healthz` remains independent liveness with its existing body. Operational responses are `no-store`. On drain, all new HTTP work, including reads, static files, SSE, and CORS preflights, is rejected with observable, logged, CORS-enabled `503` responses; only exact `GET`/`HEAD` `/healthz` and `/readyz` probes remain admitted, with readiness returning not-ready. Active probes remain tracked until force-close shuts their admission gate, so their handlers join before the watchdog stops and SQLite closes without a WaitGroup Add/Wait race. One configurable total shutdown budget includes a short HTTP drain, cancellation, forced HTTP close, and all tracked worker/request joins before SQLite closes. Local loops, archive/copy work, network requests, and restore transactions honor cancellation where tractable. If a noncancelable filesystem or SQLite critical section still exceeds the total budget, a process watchdog logs a critical fail-closed message and exits without closing SQLite under live goroutines rather than hanging until the platform sends `SIGKILL`. Locale, lyrics, source, and restore mutations/accesses write content-minimized audit rows. Editor mutations accept only the closed translation source vocabulary `cn`, `human`, `pinned`, `llm`, and `unknown`; invalid category-batch, legacy entry, event, or applicable lyrics translation-source values return `400` before persistence.

## Public Files

Legacy `/files/translation/*` and `/translation/*` generation, ETags, CORS, and cache policy are unchanged. Additive assets include:

- `/files/v2/{locale}/translation/{category}.json`
- `/files/v2/{locale}/translation/{category}.full.json`
- `/files/v2/{locale}/translation/eventStory/event_{eventId}.json`
- `/files/v2/data/search-index.json` and `/files/v2/en-US/data/search-index.json`, retaining `n`/`cn` and adding optional `en`
- Published-only lyrics index/detail files under `/files/translation/lyrics/` and each locale's `/files/v2/{locale}/translation/lyrics/`; `/translation/lyrics` and `/translation/lyrics/` are literal aliases for `/translation/lyrics/index.json`

Lyrics assets rebuild as one set. A malformed publication preserves the complete previous set rather than exposing a partial index/detail update. For the production lyrics overlay, the standalone image additionally embeds the accepted public-only v3 runtime bundle `server/internal/publiclyricsbundle/public-v3.tar.gz`. The bundle is a self-describing closed inventory with bidirectional 1-to-1 completeness (index songs in complete/game_only states exactly match detail files) containing only `index.json` and `music_<id>.json`; it contains no manifest, receipt, producer SQLite database, recovery evidence, or private input. On every files-service projection rebuild the embedded bundle is the reviewed immutable base, and the database-backed lyrics projection overlays it: a database publication whose state is `complete` or `game_only` with a revision greater than the bundle entry, a publication for a music ID absent from the bundle, or any newer non-draft publication replaces or adds that index entry, marks the music ID as database-owned, and replaces its detail bytes; the merged index is re-marshalled with the same deterministic generator marshalling and trailing newline, and the merged canonical set is mirrored to all supported locale mirrors under `v2/{locale}/translation/lyrics/`. Draft or incomplete database states never override a reviewed `complete` or `game_only` bundle entry, and a failed database projection serves the pure bundle bytes (fail-closed to the reviewed release). This is a runtime publication overlay only: it never replaces or mutates the production SQLite database, and it is not copied into Git/S3 content backups. A successful `POST /api/lyrics/publish` or `POST /api/lyrics/unpublish` mutation requests an immediate files-service rebuild (`PublishNow`), so newly published lyrics reach the public site without waiting for the debounced rebuild.

Raw event scenario snapshots are authenticated/private data and are never added to legacy or v2 public JSON generation.

## Backup And Restore

Git and S3 backups retain the legacy category/event `translations` restore projection, physically archive the SQLite-snapshot public lyrics projection as `translations/lyrics/index.json` and `translations/lyrics/music_<id>.json`, and add `translation-content/manifest.json`. The archived public lyrics bytes must exactly equal the corresponding `PublishedLyricsJSON` bytes from the same SQLite snapshot. `Generator.WriteAllContext` keeps its general legacy category/event output contract; `materializeBackupPayload` explicitly adds public lyrics assets only to the backup archive from the snapshot-backed generator. Both backup projections are materialized from one SQLite snapshot; manifest schema version 1 checksums and counts multilingual entries, stable event content, catalog/lyrics drafts, source provenance, and publication snapshots. Drafts, private provenance, and publication database state remain preserved by `translation-content/lyrics.json` so restore can reconstruct the editable SQLite state. The standalone image's accepted 700-song runtime bundle is separate immutable release content: it is not exported into these backups, is not written into SQLite during restore, and remains the reviewed base that the restored database projection overlays again after the next files-service rebuild. V2 locale projections and search indexes are not archived. Backup push is content backup only, not deployment, static publication, or CDN synchronization. Legacy and additive restore data commit in one transaction, failure rolls everything back, and backups without the additive directory explicitly clear multilingual/lyrics-only state while retaining the old database-backed public restore projection. If the target already contains native Public Lyrics source-v3 documents, application-level content restore replaces them atomically: it suspends the source-document delete guards inside the restore transaction and reinstates them before commit. User tables, password hashes, settings, token generations, audit records, and secrets are not exported. Consequently this content backup is not a full database backup. `BackupAll` fails, does not advance `LastBackup`, and does not consume scheduler success when both targets are disabled.

Schema-version-1 `translation-content/event-stories.json` additionally contains canonical scenarios. Its legacy `count` remains segments + localizations + locale metadata, while optional `scenarioCount` validates the new rows; SHA and parent/scenario identity are checked before the restore transaction replaces anything. Older additive or legacy backups without scenarios explicitly clear scenario snapshots.

Restore safety limits keep ordinary files at 64 MiB while allowing only `translation-content/event-stories.json` up to 512 MiB; expanded archives remain bounded at 1 GiB, compressed S3 responses at 256 MiB, and additive content at 1,000,000 aggregate typed records.

Production operations must additionally create full SQLite snapshots with SQLite's online backup API, `.backup`, or `VACUUM INTO`, verify `PRAGMA integrity_check`, encrypt the snapshot, and transfer it to independently controlled off-host storage. Copying only the main `.db` file while WAL writes are active is not a valid backup. Full snapshots require tested retention and restore procedures and must be taken before migration v9 and before rollback-sensitive releases.

## Authentication And Operations

JWTs carry a persisted per-user token generation and are accepted only while the user still exists and the current database role and generation match. Password changes and role changes advance the generation, deletion removes the validation row, and all three operations immediately reject previously issued tokens. Public setup and login attempts are bounded in memory by both the normalized account and the socket `RemoteAddr`; forwarding headers are intentionally ignored. First-admin creation performs the empty-user check and insert in one immediate SQLite transaction.

Editors may proofread individual entries, event lines, and lyrics drafts. CN sync, every AI trigger, event retry/reorder/promote, backup push/restore, user/settings/upstream administration, and lyrics publication are admin-only; read-only status and catalog endpoints remain available to authenticated editors.

Production rollback is defined in `ROLLBACK_RUNBOOK.md`, including immutable artifact/image selection, database migration compatibility, credential/key handling, and post-rollback verification.

Production mode is explicitly enabled with `MOESEKAI_PRODUCTION=true`. The standalone image both persists that value and replaces the development server with a binary link-stamped as `next-production`, so a deployment-level empty/false/case/whitespace override is rejected instead of disabling production checks. The image also persists the server-owned explicit selector `WORKSPACE_MODE=disabled`, the immutable bundled console root `WEB_DIR=/app/web`, `DB_PATH=/data/moesekai.db`, `DATA_DIR=/data`, and exact `TZ=UTC`. `WORKSPACE_WEB_DIR` and `WORKSPACE_MANIFEST_SHA256` must be unset in this mode; any missing or non-exact production `WEB_DIR`, `DB_PATH`, `DATA_DIR`, or `TZ` fails during `--verify-runtime` before the persistent data path is touched. Production startup then sets `time.Local = time.UTC`, so an inherited `/etc/localtime` cannot alter process-local time. The entrypoint runs that preflight before database ownership/open, upstream validation, or worker construction, and normal startup repeats it. Any missing, malformed, or conflicting workspace mode selection fails startup; a bounded tolerant percent-decoder continues past malformed inner escapes, so decoded/normalized escaped separators, backslashes, valid or malformed nested encodings, encoded dot segments, or other noncanonical paths entering the retired workspace fail closed with secure `404 no-store` handling before preflight and ServeMux. Production also requires at least 32 bytes of `MOESEKAI_MASTER_KEY` secret material and at least one initialized admin; a fresh database must receive a valid `ADMIN_PASSWORD` or `TRANSLATOR_ACCOUNTS` bootstrap secret. `editor` and `admin` are the complete role vocabulary: user creation, login, token issue/verification, and startup reject any other persisted role. Development and tests retain setup defaults and may use a short or absent master key, but external workspace artifacts remain verifier-only and are never mounted by a running server. Seed migration reconciles only nonconflicting flat/full unions, verifies the complete union through SQLite, and fails startup rather than falling through to an empty database. Publication uses a directory-durable incomplete marker; an unconfirmed post-rename target is removed or rejected by the entrypoint instead of being accepted on restart. Settings patches reject unknown keys before transaction commit, and `backup.daily_hour` accepts only canonical integer strings from `0` through `23`, so a mixed invalid patch cannot partially persist.

## Web Console

The existing setup/login/settings/AdminModal/CN sync/AI/backup/entry save/save-next/shortcuts surfaces remain mounted. Current imports derive event segment identity from event/scenario/episode plus invariant original scenario position and field (`body` or `speaker`), never from filtered JP/CN output order; migrated filtered IDs remain explicitly opaque until reconciled by a current import, and Japanese rows remain addressable when Chinese is missing or source-equal. The console adds a locale selector and filter-independent shared dirty guard for locale, field/category/mode, row, arrow, Escape, logout, AI/retry/reorder reloads, collaborator event reloads from both event SSE names, and browser-unload transitions; localized updates use locale-specific SSE event names that old Chinese clients ignore. Any SSE disconnect locks content writes, and every reconnect performs an authoritative reload before unlocking. A `content.restored` event bypasses the ordinary save-first guard: stale buffers are captured only for explicit export/manual merge while the restored server version is loaded, so the revision-free compatibility entry route is not called by that conflict flow. The responsive lyrics workspace adds catalog search with stale-response suppression, source preview, performer selection, multilingual preview, optimistic conflict recovery, guarded song/publication transitions, draft save, and admin publication controls.

The console uses the atomic local-storage envelope `moesekai-session-v1`, version 1 `{epoch, session}`, plus Web Locks `moesekai-workspace-identity` and `moesekai-workspace-refresh`. The retired schema-v3 workspace artifact retains the same client contract only for nonproduction verifier compatibility; no running server mounts or serves that client. Login and refresh publish only after identity/token-version CAS; logout and terminal token-bound 401s publish a fresh-epoch null-session tombstone, while `/auth/me` network and 5xx failures preserve the envelope and expose an offline retry state; storage events propagate refresh, account switch, and logout to SSE/UI consumers. The web clients open `/sse` with fetch streaming and the current envelope JWT only in `Authorization: Bearer`; query-token authentication is rejected, no normal JWT enters an SSE URL or log path, and every bounded-backoff reconnect rechecks the accepted epoch and current token. A valid envelope is never replaced by split-key migration, legacy keys migrate once under the identity lock, and malformed envelopes or roles outside `editor`/`admin` are unauthenticated. This prevents stale tabs from restoring an old identity or token while preserving offline verification of the retired client contract.

Official-CN and JP-pending sync validate and canonicalize every JP episode scenario before calling the event replacement transaction; one failed fetch or validation skips the complete event. A pre-pass safely fills missing or stale scenario side rows for already official/human-preserved events without changing titles, translations, sources, revisions, or public files.

The standalone production image explicitly sets `WORKSPACE_MODE=disabled`, `WEB_DIR=/app/web`, `DB_PATH=/data/moesekai.db`, `DATA_DIR=/data`, and `TZ=UTC`, copies no external workspace, and requires both external workspace variables to remain unset. A missing or overridden bundled static root, database path, data directory, or timezone fails before `/data` is touched, and Go's process-local timezone is then forced to UTC. The server claims literal, decoded, and normalized paths that enter `/workspace` before the lifecycle admission and root admin-console handler, including escaped separators/backslashes, valid or malformed nested encoding, and dot-segment forms; every such request and method returns `404` with no SPA fallback. This preserves route isolation without creating an optional frontend dependency. The Dockerfile's default final `next-production` stage makes all of `/app`, including binaries and exported console files, root-owned and non-writable to runtime UID/GID `65532:65532`; only `/data` and explicit temporary locations are writable. CI runs it with a read-only root, a persistent `/data` volume, and a bounded `/tmp` tmpfs; proves the disabled routes never return console HTML, lock contention fails, persistent restart succeeds without bootstrap admin input, and `docker stop` produces a bounded clean exit. Backend-only characterization must explicitly target `runtime`. CI also emits one deterministic `nexttrans-rollback.tar` containing mode-preserving binaries, exported web files, and `SHA256SUMS`.

The production release workflow is manual-only, restricted to protected NEXT `main`, and accepts no source, tag, release, token, or artifact inputs. Its unprotected read-only `prepare` job selects the latest matching `main` push CI attempt for the release SHA and requires that exact attempt to have succeeded, resolves the attempt-qualified candidate and rollback artifact IDs/digests, downloads both by immutable artifact ID, compares the downloaded ZIP bytes with GitHub's recorded SHA-256 digests, validates closed inventories plus candidate metadata/file hashes/bases and the rollback tar's closed path/type/mode/checksum contract, and records those exact review inputs including the rollback tar SHA-256. Only the dependent `publish` job uses the protected `production` environment, so approval is bound to the prepare outputs rather than a later same-SHA rerun. After approval it rechecks live `main`, redownloads and revalidates both exact artifacts, requires the rollback tar SHA-256 to equal its preapproval value, loads the tested image ID, and only retags/pushes it to one unused run-scoped staging tag. The ordinary `GITHUB_TOKEN` has `packages: none`; Docker and Cosign receive package-write authority only from the protected production environment's dedicated GHCR writer credential, and organization/package policy must prevent branch-modified workflows from restoring ordinary token write access. Push CI is the only image build; release never rebuilds or reads release-time base variables.

The custom NEXT-only predicate records the NEXT repository/revision/ref, exact release workflow path and SHA, exact successful CI run, candidate and rollback artifact names/IDs/archive digests, candidate file hashes, rollback tar SHA-256, standalone target and CI-recorded digest-qualified bases, and image repository/digest. Verification constrains the GitHub Actions issuer, exact `release-next.yml@refs/heads/main` certificate identity, and exact NEXT workflow SHA, then decodes the cryptographically verified DSSE statements and requires at least one exact statement whose type, subject, digest, predicate type, and complete predicate JSON match. Historical valid statements may coexist but cannot substitute for the current exact predicate. Immediately before final creation the workflow rechecks the live main tip. Operators must freeze protected-main updates from approval through final-tag verification because the GitHub branch query and GHCR tag write cannot be one atomic operation. Only after mandatory verification does it publish the single final commit-addressed tag `next-<next-full-sha>`. An existing same-digest tag is idempotent; a different digest fails. No floating tag is created. A failure after the final-tag request is an ambiguous registry outcome and requires digest inspection before retry. The same custom predicate is additionally published through GitHub's artifact-attestation service with registry push disabled only when the explicitly configured repository capability variable is enabled; the promotion job does not claim to be the image builder. Repository-wide concurrency, the branch freeze, registry tag immutability, and restriction of package-writer access to this workflow are mandatory to close publication races. Publication is environment-gated and produces a final digest but does not change a running service.
