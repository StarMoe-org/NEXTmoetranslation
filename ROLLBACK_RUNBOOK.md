# Production Rollback Runbook

## Production Build Path

Production is not deployed from a CI release artifact. Zeabur builds the Dockerfile's default `next-production` target from source at this repository's `main` and runs it as the single backend instance with the persistent `/data` volume. The deployed version is therefore a `main` commit SHA, and an application rollback means redeploying the last known-good `main` commit onto the same volume. The CI candidate/rollback artifacts and the signed `release-next.yml` image described in `STANDALONE_RELEASE.md` apply only if a deployment switches to that image; the image-specific steps below are marked as such.

## Deploy Checklist

Migrations v35 (`song_lyrics_public_withdrawals`), v36 (`lyrics_provider_page_targets`), v37 (`lyrics_source_artifacts_projectsekai_fandom_origin`), and v38 (`lyrics_recovery_takeovers`) are forward-only. `main` currently ends at v34, so the first deploy of this branch takes the v34→v38 path: one startup applies v35, v36, v37, and v38 in order, each in its own transaction, and before v35 writes the one automatic backup `/data/moesekai.db.pre-migration-v35.bak` (`<DB_PATH>.pre-migration-v35.bak`); no backup is written for v36–v38. That file is the pre-upgrade recovery point. If startup stops partway, the next start writes a backup named for the then-first pending version, and the v35 file stays the one that holds the v34 database. Once a database records v38, an older build refuses to open it (`database migration version 38 is newer than this binary`), so rolling the code back means restoring the pre-migration backup and losing every write made after it. The policy is forward-fix: repair the new release in place and restore only when that is impossible.

v37 rebuilds one table, `song_lyrics_source_artifacts`. It copies every row unchanged, recreates the table's index and its three triggers, and widens only the `vocaloid_fandom` origin check so it also accepts `https://projectsekai.fandom.com`. It runs with foreign keys off inside the migration transaction, and a `PRAGMA foreign_key_check` violation rolls it back. Measured cost: `TestMigrationV37RebuildsSongLyricsSourceArtifactsVerbatim` opens a v36 database holding the embedded seed's 787 artifact rows and applies v37 and v38 in about 0.8 s, including the pre-migration backup and the full integrity check. Those two steps scale with the size of the whole database, so estimate startup time from the database size rather than the artifact count.

v38 only creates the empty table `lyrics_recovery_takeovers` with one index and three RAISE-only triggers; it writes no row and changes no existing table (`TestMigrationV38OnlyCreatesTheTakeoverTable`). The table fills later: the first non-`dryRun` `PUT /api/editor/v1/lyrics/document` or successful `POST /api/editor/v1/lyrics/document/takeover` for a song held by the recovery import ledger records a takeover row there, leaving the ledger rows unchanged; its nullable `localizations_json` column keeps the `zh-CN` translations of a superseded source-v3 document (see `contracts/editor-api/README.md`). Once any takeover exists, offline `lyrics-recovery-import` refuses every new recovery batch, because a batch covers the whole catalog and may not add an item for a taken-over song. It refuses the same way for any song whose source document the lyrics editor owns (`refuseRecoveryItemsForEditorOwnedSongs`): a song published through `PUT /api/editor/v1/lyrics/document`, song 682 as migration v32 wrote it, or an embedded editor seed song. A database on which v32 wrote song 682 therefore already refuses every new recovery batch, and replaying an imported batch still works.

Before deploy:

1. Pause editor writes and producers (CN sync, AI translation, scheduled backup) and record the current `schema_migrations` head and the deployed `main` SHA.
2. Take a full snapshot with `VACUUM INTO '<snapshot-path>'`, run `PRAGMA integrity_check` on the snapshot (it must return `ok`), and move it off-host.
3. Require free space on `/data` of at least twice the database size. Before the first pending migration, startup writes `<DB_PATH>.pre-migration-v<N>.bak` beside the database with `VACUUM INTO` (through a `.tmp` file), where `N` is the first pending version; a snapshot kept on the same volume needs room as well.
4. Check the environment ranges; an invalid value stops startup:
   - `SHUTDOWN_BUDGET_MS` (default `25000`) and `SHUTDOWN_DRAIN_MS` (default `2000`) are positive integer milliseconds with drain shorter than budget.
   - `LYRICS_DISCOVERY_ENABLED` and `LYRICS_FETCH_REVISION_ENABLED` are validated on every start, not only the first, and must be exactly `true` or `false`.
   - Parsed only while `lyrics_discovery.enabled` is true: `LYRICS_DISCOVERY_SCAN_MS` 60000–604800000 (default 21600000), `LYRICS_DISCOVERY_LEASE_MS` 10000–86400000 (default 120000), `LYRICS_DISCOVERY_IDLE_MS` 100–60000 (default 2000), `LYRICS_DISCOVERY_RETRY_MIN_MS` 1000–86400000 (default 30000), `LYRICS_DISCOVERY_RETRY_MAX_MS` 1000–2592000000 (default 1800000) and not below the minimum, `LYRICS_DISCOVERY_JOB_TIMEOUT_MS` 1000–600000 (default 30000) and shorter than the lease, `LYRICS_DISCOVERY_CONCURRENCY` 1–16 (default 4).
   - Parsed only while `lyrics_discovery.fetch_revision.enabled` is true: `LYRICS_FETCH_REVISION_LEASE_MS`, `LYRICS_FETCH_REVISION_IDLE_MS`, `LYRICS_FETCH_REVISION_RETRY_MIN_MS`, `LYRICS_FETCH_REVISION_RETRY_MAX_MS`, `LYRICS_FETCH_REVISION_JOB_TIMEOUT_MS`, and `LYRICS_FETCH_REVISION_CONCURRENCY`, with the same ranges and cross-checks as their discovery counterparts.

After deploy, before reopening writes:

1. `GET /readyz` returns `200` (it waits for the first public projection).
2. `GET /files/translation/lyrics/index.json` returns the index.
3. `GET /files/translation/lyrics/music_<id>.json` for one `complete` index entry returns a detail with `"version": 3`.
4. `POST /api/auth/login` as an administrator succeeds (each attempt counts against the 10-per-5-minutes login limiter).
5. One v1 write without `X-Moe-Loaded-Producer-State`: `PUT /api/editor/v1/entry` re-submitting an existing entry's current `text` and `source` returns `200 {"status":"noop"}`.
6. As the administrator, `GET /api/editor/v1/lyrics/document?musicId=<id>` for a `complete` index entry returns `200` with `"from": "served"`, a `document` whose `expectedRevision` is set, and a `warnings` array. Pick an entry the PUT accepts. Its `warnings` must contain none of `source_missing`, `source_unsupported`, `ruby_not_served`, `ruby_not_expressible`, or `credit_missing`, and its `document` must have at least one line with `zh`; a document with no credited rendition or no `zh` line is refused with `422 invalid_lyrics_document`. Add `"dryRun": true` to that `document`, keep its `expectedRevision` (without it the PUT returns `422 expected_revision_required`), and send it as `PUT /api/editor/v1/lyrics/document`: it returns `200` with `"dryRun": true`, a `document`, and `"changes": {"against":"served","changed":false}`, and commits nothing: the dry run performs the publish writes and rolls them back. Then send `POST /api/editor/v1/lyrics/document/takeover` with the body `{"musicId": <id>}` only: it returns `422 expected_revision_required` whose `current.revision` equals the exported `expectedRevision`, and writes nothing. A song held by the recovery import ledger is a valid choice, because the dry run rolls back its takeover row and the refused takeover writes nothing.
7. As the administrator, `GET /api/editor/v1/lyrics/document?musicId=682` returns `200` with `"servedVersion": 4` and a `document` whose `translationEditions` lists both of song 682's editions with the default first (migration v32 created `main` labelled 雪莹ちゃん, the default, and `aishitenryu` labelled 爱死天流). Add `"dryRun": true` to that `document`, keep its `expectedRevision`, and send it as `PUT /api/editor/v1/lyrics/document`: it returns `200` with `"dryRun": true`, a `document` with `"version": 4`, and `"changes": {"against":"served","changed":false}`. A `500 internal_error` or any listed change fails this check: the release would not republish a song with translation editions intact.
8. `schema_migrations` ends at `38` (`lyrics_recovery_takeovers`), read through an approved operator tool, and the pre-migration backup for the first pending version exists beside the database: `/data/moesekai.db.pre-migration-v35.bak` when the deploy started from v34.
9. Trigger one content backup from the console (it sends the required producer-state header) and confirm it succeeds. Before this release, a database holding embedded-seed or document-route songs failed export with `lyrics source artifact evidence … has no exact parent evidence`.

## Trigger And Ownership

Use this procedure for a bad application artifact or container image, a failed rollout, or a schema-related startup failure. Assign one incident owner, stop automated deploys, backup jobs, CN sync, AI translation, and all editor writes, and record the current artifact digest, Git revision, database path, database migration version, and UTC time before changing anything.

## Preserve Evidence And Recovery Inputs

1. Keep the failed immutable artifact or image digest available for diagnosis; never overwrite its tag.
2. Create a full SQLite snapshot with the online backup API, `.backup`, or `VACUUM INTO`, then run `PRAGMA integrity_check`, encrypt it, and transfer it to independently controlled off-host storage before rollback. Do not copy only the main file while WAL writes are active. The application Git/S3 `translation-content` backup is not sufficient because it omits users, password hashes, token generations, settings, audit state, and encrypted configuration.
3. Retain the automatic `*.pre-migration-vN.bak` file and verify it opens before relying on it.
4. Preserve application logs, request IDs, deployment events, and the exact environment-variable names in use. Do not place secret values in tickets or logs.
5. Image-based deployments only: download the CI artifact named `rollback-<full-git-sha>-<ci-run-attempt>`, which contains only `nexttrans-rollback.tar`. Require its artifact ID and SHA-256 digest to match the released image's custom predicate. Extract it into an empty directory, verify `sha256sum -c SHA256SUMS`, and confirm `moesekai-server` and `moesekai-migrate` retain mode `0755` before use. The server binary is link-stamped with the same non-overridable `next-production` runtime profile as the released image. The deterministic tar contains both binaries, the complete exported `web/` tree, and its internal checksums; CI builds it twice and requires byte equality. Candidate and rollback artifacts are immutable but retained for only 90 days, so archive both durably with their artifact digests before rollout. Container operations must separately record the digest-qualified three base images and final image digest.

## Artifact Or Image Rollback

1. For the Zeabur source build, select the last known-good `main` commit SHA and redeploy exactly that commit. For an image-based deployment, select the last known-good final image digest from the standalone release record, not a tag. Verify its OCI labels and custom NEXT-only predicate agree on the NEXT revision, exact release workflow SHA, successful CI run, standalone target, digest-qualified bases, image repository, and final image digest. The commit-addressed `next-<next-full-sha>` tag is a discovery aid only and must never be rewritten during rollback.
2. Use a `Recreate` rollout for this service: stop the current instance before starting the replacement. The editor gate and SQLite writer are process-local, so two backend replicas must never serve concurrently. A separately replicated static frontend must not imply replicated backend writers.
3. Deploy the known-good artifact with the same persistent data mount and network policy only after completing the database compatibility decision below.
4. Keep the failed version unavailable to traffic until verification completes.

## Database Compatibility Decision

1. Read `schema_migrations` from the affected database and compare its highest version, name, and checksum with the rollback binary.
2. If the rollback binary recognizes the current migration history and its documented behavior is compatible, retain the current database. Never edit `schema_migrations` to make an old binary start.
3. If the rollback binary is older than the database history, restore the verified pre-migration backup created immediately before the first unsupported migration. Do not downgrade tables in place.
4. Migrations v35-v38 are forward-only. A binary that does not recognize v38 must not open a v38 database: stop the service, restore the verified `*.pre-migration-v<N>.bak` for the first pending version of the rollout (`*.pre-migration-v35.bak` when it started from v34) or the pre-rollout off-host snapshot, then apply the token invalidation step below. Every recovery-ledger takeover recorded after that point is lost with the other writes. Do not restore a content backup made by this release into an older build: once a song cites `https://projectsekai.fandom.com`, the older schema's origin check rejects that artifact, and once a takeover exists, `translation-content/lyrics.json` carries `recoveryTakeovers`, which the older build's strict decoder rejects as an unknown field.
5. Migration v9 (`retain_rolling_event_segment_recovery_rows`) changes event segment uniqueness. A binary that does not recognize v9 must not open the v9 database. Stop the service and restore the verified backup created before the first pending migration in that rollout: this is `*.pre-migration-v9.bak` only when v9 was the first pending migration, and may instead be `*.pre-migration-v8.bak` for a v7→v9 jump. If that recovery point is too old, use the pre-rollout full off-host snapshot. Then apply the token invalidation step below.
6. Restoring a database also restores user token generations, drafts, publications, and audit state to that point. Before restarting, invalidate every token that the restore could revive: either rotate `JWT_SECRET` to fresh signing material or, in one audited transaction against the stopped database, increment `users.token_version` for every user. Record this security and data-loss window and require all users to reauthenticate. Do not return traffic until one of these invalidation steps is verified.
7. After database restore, regenerate public assets from that database; do not combine public files from one revision with SQLite state from another.

## Keys And Credentials

1. Keep `MOESEKAI_MASTER_KEY` stable when retaining or restoring encrypted settings; changing it makes existing encrypted values unreadable. Production keys contain at least 32 bytes of secret material and should be generated once with `openssl rand -base64 32`, then retained in the deployment secret manager.
2. Keep `JWT_SECRET` stable only for an ordinary artifact rollback that retains the current database. A database restore requires the JWT rotation or global `users.token_version` increment above; suspected signing-material exposure always requires rotation. Require all users to log in again after either event.
3. Do not restore revoked Git, S3, upstream, or LLM credentials from an old environment snapshot. Reapply the current secret-manager values and least-privilege policies after rollback.
4. Verify Git backup branch protections and S3 bucket/versioning policy before re-enabling backup push.

## Verification Before Traffic

1. Image-based deployments only: verify the selected digest's keyless image signature and custom NEXT-only attestation against issuer `https://token.actions.githubusercontent.com`, the exact `release-next.yml@<default-branch-ref>` certificate identity, and the recorded NEXT workflow SHA. Strictly compare the predicate's NEXT source revision, CI run, standalone target, digest-qualified bases, image repository, and image digest with the incident record. For every deployment, inspect the running configuration and require `MOESEKAI_PRODUCTION=true`, `WORKSPACE_MODE=disabled`, exact `WEB_DIR=/app/web`, exact `DB_PATH=/data/moesekai.db`, exact `TZ=UTC`, no external workspace variables, UID/GID `65532:65532`, UTC zoneinfo data, and no `/app/workspace`. Start one isolated instance with a read-only root, the restored persistent `/data`, and bounded `/tmp`; require `/workspace`, `/workspace/`, a nested client route, and an asset-like route all to return `404` without console HTML. Require `/readyz` success only after the asynchronous initial public projection publishes; check independent `/healthz` liveness and admin-authenticated `/healthz/details` without exposing counters publicly. Confirm all operational responses are `Cache-Control: no-store`.
2. Confirm the expected `schema_migrations` rows and open the database with `PRAGMA integrity_check` through an approved operator tool.
3. Log in as an editor and an administrator. Confirm stale tokens from changed/deleted accounts fail, editor proofreading works, and editor requests to sync, AI, retry/reorder, and backup push return `403`.
4. Load `GET /api/editor-gate/status`, verify its process-specific `instanceId`, and exercise a `/api/editor/v1/*` write both without `X-Moe-Loaded-Producer-State` (admitted leniently) and with the revision-bound `<instanceId>:<revision>:<completedGeneration>` proof. Independently confirm that a stale revision with unchanged instance/generation, a stale pre-restart instance, or a stale completed generation returns `409` with current status, and that a malformed header returns `400`. `POST /api/editor/v1/backup/push` without the header must still return `428` (the gate refuses it before any backup runs). Do not restore traffic if the gate reports `running` or its counters violate `completedGeneration <= generation`.
5. Fetch representative legacy no-locale category and event assets and compare their shape to the compatibility fixtures.
6. Fetch the canonical Public Lyrics v3 `index.json`, one `complete` detail, one top-level `game_only` detail, and confirm an `incomplete` entry has no detail artifact. Strictly validate the index/detail bytes against `contracts/public-lyrics/v3/`, verify the manifest/receipt catalog and detail counts, and confirm public attribution is present while private source fields are absent. Also verify the corresponding legacy v2 assets remain byte-identical to the recorded release candidate.
7. Perform a dry-run or non-pushing content-backup materialization (it must succeed on a database that holds embedded-seed or document-route songs), verify the translation-content manifest counts include rendition localizations and rendition translation lines, verify checksums, and confirm the lyrics attribution and plural rendition credits/text round-trip. Application-level `translation-content` restore replaces native source-v3 documents atomically (it suspends their delete guards inside the restore transaction and reinstates them before commit), so never run it against the live database as a verification step. Separately restore the encrypted full SQLite snapshot in isolation, run `PRAGMA integrity_check`, and verify users, settings, audit rows, token generations, source-v3 artifacts, contributions, and rendition localizations are present.
8. Restore traffic gradually to the single backend instance, monitor request IDs and error counters, then re-enable backup, sync, and AI jobs one at a time.

## Forward Recovery

Prefer a fixed forward release after service is stable. It must accept the restored/current migration history, rerun all uncached Go, race, vet, Web contract, formatting, and diff checks, and use a new immutable artifact or image digest. Record the rollback and forward-recovery revisions, database decision, credential rotations, and verification evidence in the incident log.
